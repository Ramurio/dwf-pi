## 2. Находки

### R10-B01 — Старый список возвращает прежний статус после нового списка

**Класс:** bug. **Фактический код:** `src/graph-view/app.js:1485–1495,1508–1511`. Источники конкурирующих вызовов — `1531` (follow-up control) и `1643` (poll). Для сравнения, snapshot имеет собственный счётчик запросов на `1451–1455`.

**Триггер.** Обычный `refreshRuns()` уже отправлен; пользователь нажимает «Пауза». `control('pause')` успешно получает POST, актуальный snapshot и свой новый список. После этого заканчивается прежний GET списка. Оба вызова относятся к тому же посещению — все уже исправленные visit guards законно возвращают true.

**Ожидание.** Принятый более новый список не должен заменяться результатом более раннего запроса. Его запоздалый отказ не должен перекрывать успешное обновление списка/снимка сообщением об отсутствии связи.

**Наблюдение в настоящем Chrome, fixture `list`.**

1. После control follow-up: `state.runs[0].status = paused`, `state.run.status = paused`.
2. После release старого GET: список = `waiting`, детали = `paused`; sidebar снова показывает «Ждёт ответа».
3. Новый явный `refreshRuns()` возвращает sidebar в `paused`.
4. В отдельной последовательности старый GET завершается ошибкой **после более нового успешного GET списка и snapshot**: notice = `OLDER_LIST_FAILURE`, connection = `Нет связи`.
5. Управляющий POST в fixture ровно один.

**Причина.** `refreshRuns` принимает только внешний `isCurrent` (по умолчанию всегда true). Нет собственной идентичности/очерёдности чтения списка. `listSignature` проверяет лишь различие данных и потому охотно принимает старое, но отличающееся содержимое. Существующий control guard решает другую задачу — уход с исходного посещения.

**Контрдоказательства и масштаб.** Исправление snapshot не сломано: детали сохранили `paused`. `graph-view-observation.test.ts:532–613` успешно проверяет control follow-up после перехода на другой запуск и актуальный unscoped refresh. Эти тесты не переставляют местами два списка в одном посещении. Последовательный обычный polling сам с собой не пересекается: следующий timer ставится в конце `poll`. Нужен второй источник чтения, здесь control follow-up. Потеря команды или серверного состояния не наблюдалась.

**Минимальная рекомендация, не внедрена.** Дать `refreshRuns` собственное поколение чтения и объединить его с существующим `isCurrent`; проверять актуальность до глобального эффекта 401, после JSON и в catch. Не заменять visit guard одним run ID.

**Риск изменения.** Можно нечаянно подавить полезное глобальное обновление sidebar после навигации либо начальный выбор запуска. Сохранить обычный unscoped refresh и recovery текущего 401.

**Критерий приёмки.** Два concurrent reads списка в одном посещении: новый success → старый success/body decode/network error/401 не меняют принятые данные и feedback. Контрпроверки: текущий success/401 работает; существующие A→B→A/control tests остаются зелёными. Выполнены success и network-error варианты; body/401 для нового list-order guard — **предложенные** проверки.

### R10-B02 — Polling не даёт закончить медленную загрузку «Вся задача»

**Класс:** bug. **Фактический код:** `src/graph-view/app.js:294–306,1470–1474,1632–1648`; дополнительно `src/graph-view/task-scope.js:116–122`. Неподписанная подмена суммы: `app.js:1322–1339`.

**Триггер.** Выбрана «Вся задача», snapshot отвечает быстро, а `task-usage` отвечает медленнее интервала между snapshot refresh. Каждый refresh без ожидания запускает новую загрузку task scope и увеличивает `state.taskFetch`. Порог — фактический интервал polling, не обязательно ровно секунда: он включает длительность snapshot/list.

**Ожидание.** Успешная загрузка текущей задачи должна завершиться и быть показана, даже если она медленнее polling. Пока результата нет, нельзя выдавать расход одного запуска за выбранную всю задачу без явной оговорки.

**Наблюдение, fixture `task`.** Использован production `poll` без изменения его интервала. Fake `task-usage` успешно отвечает через 1600 мс; остальные ответы немедленные. За 4400 мс:

- 5 запросов `task-usage`, 4 polling snapshot и 1 GET списка;
- **0** запросов `task`, `state.taskUsage = null`;
- выбран режим task, «Всего» показывает **0** — сумму текущего запуска, хотя fake task summary = **30**;
- после остановки **только fixture polling** последний уже начатый запрос заканчивается: 1 GET task, сумма становится **30**, без изменения API и без нового пользовательского выбора.

**Причина и вывод.** `seq = ++state.taskFetch` защищает от старых данных, но запуск новой загрузки не учитывает существующий in-flight запрос того же scope. Возвращающийся ответ отбрасывается на `299`, ещё до чтения членов задачи. На `306` есть такая же защита для более поздних стадий. При сохранении данного порядка задержек отбрасывание будет повторяться; непосредственно наблюдались четыре polling-цикла, не «бесконечный live прогон». На экране нет loading/stale-маркера task totals: пока `taskUsageForView` возвращает null, renderer берёт `state.run.usage` при уже выбранной кнопке «Вся задача».

**Контрдоказательства.** Та же fixture с 20 мс (`task-fast`) успешно выполняет 5 task loads, показывает **30** и при работающем polling. Отключение только timer позволяет завершиться медленному запросу. `graph-view-task-scope.test.ts:38–145` успешно проверяет идентичность task и producer navigation, но не liveness загрузки под периодической инвалидацией. B02 не означает смешивание сумм разных task: существующее ограждение identity остаётся полезным.

**Минимальная рекомендация, не внедрена.** Для одного актуального `(taskId, visit)` переиспользовать незаконченный Promise/не начинать очередной task load, пока он не завершён; поколение менять при настоящей смене scope/посещения, а не уничтожать каждую медленную попытку обычным poll. Явно показывать «загрузка/последние данные задачи»; не маркировать сумму run как task total. Это не ограничение параллелизма графа и не новый retry.

**Риск изменения.** Слишком широкий task-key может вернуть старое посещение или блокировать загрузку после A→B→A. Нельзя убирать task/visit guards или перестать обновлять расход после первого успеха.

**Критерий приёмки.** При том же 1600-мс fake API и продолжающемся production polling task total появляется; нет очереди взаимно инвалидирующих одинаковых загрузок. Затем рост total показывается без смены вкладки. Во время ожидания подпись соответствует scope. Обязательны A→B→A и смена task во время каждого await. Последние дополнительные сценарии — **предложенные**, исправление не проверялось.

### R10-B03 — Старый GET истории скрывает только что сохранённое решение

**Класс:** bug. **Фактический код:** `src/graph-view/app.js:848–860` против `744–748`. Второй писатель в те же кэши — inspection на `674–676` (прочитан, отдельная его перестановка не воспроизводилась).

**Триггер.** Инспекция операции уже загружена, форма решения доступна. Пользователь открывает «Решения о восстановлении»: GET прочитал прежний пустой список, но ответ задержан. Пока GET ожидает, пользователь заполняет форму и сохраняет решение. POST возвращает receipt, после чего приходит прежний GET.

**Ожидание.** После подтверждённого сохранения решения более раннее чтение не должно заменять историю пустым списком и сообщать «Сохранённых решений нет». Если показывается исторический снимок, он должен быть явно старее подтверждённой записи, а не получать время доставки как время актуального знания.

**Наблюдение, fixture `recovery`, native DOM clicks/input.**

- После POST: records = 1, `saved = true`, `draft.receipt` существует.
- После старого GET `[]`: records = 0, `saved = false`, **receipt в draft остаётся**.
- В одном инспекторе одновременно видны «Сохранённых решений нет.» и «Решение сохранено.».
- «Обновить решения о восстановлении» возвращает records = 1. Всего POST = 1, GET history = 2. Обычный snapshot не перечитывает этот кэш.

**Причина.** Обработчик GET безусловно заменяет `reconciliationRecords[runId,key]` после await; `cached` захвачен до запроса. POST независимо кладёт более новое значение под тот же ключ. Разделение по run/key правильно, но внутри одного ключа нет поколения чтения/мутации. `Date.now()` ставится при доставке GET, а не при чтении на сервере.

**Контрдоказательства и масштаб.** Это **не повторное открытие** исправления позднего receipt после навигации. `draft.request`, `decisionId` и `draft.receipt` не потерялись; новый POST автоматически не отправлен. `graph-view-observation.test.ts:221–283` проверяет именно сохранение receipt и visit ownership и прошёл. Клиентская история стала противоречивой, но потеря записи SQLite не доказана и не заявляется. Прочитанный серверный код проверяет прежний decision ID, checkpoint/attempt/workspace (`run-controller.ts:312–324`) и явный `supersedes` (`run-store.ts:804–820`); обойти эти проверки stale UI не может само по себе.

**Минимальная рекомендация, не внедрена.** Ввести поколение для reconciliation cache по `(runId,key)`; сохранение POST инвалидирует более ранние чтения. Согласовать оба писателя — отдельную history load и recovery inspection. Старый GET не должен стирать receipt/локально известную запись. Новое чтение после POST должно иметь право уточнить application/superseded status.

**Риск изменения.** Простое вечное объединение по decisionId заморозит старый статус «ожидает допуска»; глобальная блокировка GET/POST ухудшит форму и другие ключи. Нужен порядок знания, а не запрет свежего чтения.

**Критерий приёмки.** GET-before-POST → POST receipt → старый GET не убирает известное решение; GET-after-POST обновляет его состояние. Повторить для late error и inspection writer, проверить независимые run/key. Последние варианты — **предложенные** проверки.
