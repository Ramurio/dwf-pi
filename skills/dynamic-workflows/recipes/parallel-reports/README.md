# Параллельные отчёты в отдельных рабочих деревьях

Два исследователя пишут отчёты в разных рабочих деревьях Git, затем отдельный
агент сопоставляет результаты. Это пример для файловых отчётов, а не требование
всегда создавать двух агентов. Для исследования без записи файлов используй
[research-trio](../research-trio/README.md): чтение и структурированные ответы.

```text
parallel (collect)
  first  → worktree → researcher → {result, workspace}
  second → worktree → researcher → {result, workspace}
→ synthesizer (только чтение) → finish
```

Запись Markdown/JSON — такая же запись, как изменение кода. Разные имена файлов
не заменяют изоляцию. Оба вызова общего графа `isolated` выделяют **свои** рабочие
деревья; один `worktree` вокруг всего `parallel` не разделил бы их записи.
Рецепт не ограничивает параллелизм и не создаёт дополнительного планировщика.

## Подставь параметры в копиях JSON

Скопируй [create.json](create.json), [patch.json](patch.json) и [input.json](input.json)
в каталог задачи вне установленного пакета инструкций. Запросы подходят CLI/MCP
без генератора кода. Измени:

- Одинаковый `id` в create/patch и следующих запросах; `name` — название графа.
- В обоих агентных `config` файла patch — `model.provider`, `model.id`, `thinking`
  по доступному `catalog.models`. Значения `REPLACE_PROVIDER`/`REPLACE_MODEL` —
  заменяемые поля, не запасная модель. Настройка `writer/research` общая для двух
  вызовов; `main/synthesize` настраивается отдельно.
- В input — вопрос, критерии, применимые инструкции AGENTS в `projectPolicy`,
  задания `first`/`second`, `sources` и относительные `reportPath` внутри каждого
  выделенного рабочего дерева. Не используй абсолютные пути или выход через `..`.
- В `workflow.prepare` — `cwd` чистого Git-репозитория. Источники должны быть
  закоммичены и доступны по указанным путям; рабочие деревья начинаются с его HEAD.
  Не коммить временные запросы/ответы запуска ради этой чистоты: храни их вне репозитория.

Автор отчёта получает `read`/`grep`/`find`/`ls`/`write` и `workspace-write`.
Обобщающий агент получает только чтение. Веб-доступа и Bash в этом примере нет.
Если задание требует Bash, добавь разрешённый инструмент явно **внутри** каждой
изолированной ветви; профиль разрешений и рабочее дерево не являются изоляцией ОС.
Ни модель, ни разрешения не понижаются для обхода проверки графа.

## Создание и запуск

Порядок и оболочки ответов — в [основных инструкциях](../../SKILL.md).
Передай create в `workflow.create`, затем возьми фактическую `result.revision`
из ответа и подставь её в `patch.expectedRevision`. Передай patch в `workflow.patch`;
проверь `result.validation.valid`. Далее:

```json
{"id":"parallel-reports"}
```

Это запрос `workflow.validate`; продолжай только при `result.valid: true`.
Подготовка:

```json
{"id":"parallel-reports","cwd":"/absolute/clean/repository"}
```

Передай его в `workflow.prepare`, изучи `result.plan` и сохрани `result.preparedId`.
Затем вызови `run.start` с этим `preparedId`, заранее выбранным `idempotencyKey`
и полным объектом из input.json в поле `input`. Путь к input.json не заменяет
объект. При запуске по `preparedId` не повторяй `cwd`, `id` или `model`.
Сразу сообщи пользователю ID запуска и команду наблюдения; таймаут не повод
создавать другой запуск. Все команды используют один журнал `--store`.

## Где лежат отчёты и что возвращается

После успешной ветви `worktree` коммитит её изменения и возвращает:

```json
{"result":{"status":"written","reportPath":"reports/guarantees.md","summary":"..."},"workspace":{"path":"/allocated/worktree","branch":"...","base":"...","head":"..."}}
```

Узел `isolated/done` возвращает эту оболочку целиком. `collect` добавляет ещё один
уровень: сначала проверь `reports.first.status == "succeeded"`; затем сведения
автора находятся в `reports.first.value.result`, а запись рабочего дерева —
в `reports.first.value.workspace`. Для second путь аналогичен. У `failed` есть
`failure`, но нет `value`. В режиме без `collect` уровня `value` не было бы.

Физический файл находится по `workspace.path` + относительный `result.reportPath`;
коммит — `workspace.head`. После завершения всех ветвей обобщающий агент читает
эти файлы и возвращает структурированный итог. Корневой результат содержит
`reports` со всеми оболочками и `synthesis`; `accepted` требует двух успешных
ветвей со статусом `written` и положительного итога. Ошибка ветви не превращается
в принятие, даже если обобщающий агент ошибочно вернул `accepted`.

В исходный репозиторий отчёты **не публикуются автоматически**. Для публикации
добавь отдельный явный узел после сбора всех ветвей и проверки их исходов:
например, разрешённый задачей `integrate` получает массив успешных `value.workspace`
после необходимого ревью. Если нужны отдельные файлы или иные имена, их сбор задаётся
отдельной последовательной задачей после параллельной стадии. Не запускай публикацию
из самих исследовательских ветвей. Конфликты слияния и неполные отчёты требуют
обработки, а не подмены результата.

`tests/parallel-reports-recipe.test.ts` проверяет схему запросов, редактирование,
подготовку и реальную запись в Git-деревья с детерминированной заменой агентных
ответов. Это проверка без моделей; содержательную точность будущих отчётов она
не доказывает и проверенным пресетом рецепт не объявляет.
