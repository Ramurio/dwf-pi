# Реализация с независимым ревью

Три переносимых стартовых рецепта для изменения кода в выделенном рабочем дереве Git.
В каждом есть реализация, настоящая команда проверки, снимок Git-артефакта,
независимое ревью текущего артефакта и обратная связь исполнителю.

| Рецепт | Организация работы |
| --- | --- |
| [S](S/patch.json) | План → реализация → проверка → независимое ревью. |
| [P](P/patch.json) | План и предварительное ревью исходного артефакта выполняются параллельно; затем реализация, проверка и новое ревью. |
| [C](C/patch.json) | После плана, реализации и проверки два независимых ревьюера проверяют корректность и контракт. Нужны оба `approve`. |

`create.json`, `patch.json`, `validate.json` в каждом каталоге — готовые запросы
официального API создания графов; `input.json` — нейтральный пример задачи. Рецепт
переносится вместе с пакетом инструкций и создаёт новый граф под ваши параметры.
Проверенный пресет — отдельная локальная запись неизменяемого плана принятого запуска:
его команду проверки и аргументы нельзя заменить через новый `input`. Для другой
команды выполните `instantiate.mjs` и подготовку плана заново. Локальные проверенные
пресеты не устанавливаются от копирования рецепта; их имена не гарантируют качества
следующей задачи.

## Привязка к проекту

Нужны Node.js, Git и доступный Dynamicwf. Подставьте реальные файлы, критерии,
политику проекта и доступную команду проверки в копию
[parameters.example.json](parameters.example.json). Пример `normalizeLabel` лишь
показывает формат: вспомогательный скрипт не создаёт исходники или тесты этой функции.
`projectPolicy` должен явно передавать применимые инструкции проекта, поскольку
исполнители не подхватывают проектный AGENTS.md автоматически. `contextFiles` — пути
от корня будущего рабочего дерева, доступные исполнителям; проверьте их заранее.

Для новой задачи используются `task`, `acceptanceCriteria`, `projectPolicy`,
`contextFiles`, `checkCommand` и `checkArgs`; `id` и `name` относятся к создаваемому
графу. `repo` и `base` не являются параметрами `input`. Целевой репозиторий задаётся
через `cwd` при подготовке; отдельное рабочее дерево начинается от текущего чистого `HEAD`.

```sh
node /path/to/implementation-review/instantiate.mjs \
  --recipe /path/to/implementation-review/S \
  --parameters /path/to/task-parameters.json \
  --out /path/to/task-recipe
```

Команда только создаёт файлы. Она не запускает исполнителей и не обращается к сети.
Каталог результата должен находиться вне исходного рецепта; до записи проверяются
существующие символические ссылки, ведущие к исходному каталогу или его родителям.
Результат включает обновлённые запросы создания, изменения и проверки графа,
входные данные и сведения о привязке.

Передайте содержимое `create.json` в `workflow.create`. Перед отправкой
`patch.json` в `workflow.patch` установите `expectedRevision` из фактической
`revision` ответа на создание графа (в оболочке ответа CLI/MCP — `result.revision`).
Затем передайте `validate.json` в `workflow.validate`. Выполните `workflow.prepare`
с `id` нового графа и `cwd` — корнем целевой чистой рабочей копии Git, например
`{"id":"implementation-review-example","cwd":"/path/to/project"}`.
`workflow.prepare` не принимает входные данные задачи. Изучите подготовленный план
и вызовите `run.start` с полученным `preparedId`, явным `idempotencyKey` и полем `input`,
содержащим полный JSON-объект из `input.json`; путь к файлу не заменяет объект.
При старте по `preparedId` не передавайте повторно `id`, `cwd` или `model`.
Сразу сообщите пользователю идентификатор запуска. Таймаут наблюдения не означает
необходимость нового запуска. Подробные поля и команды — в [основных инструкциях](../../SKILL.md).

Команда проверки и точный список аргументов фиксируются в `patch.json`; изменение
`input.checkCommand` или `input.checkArgs` не меняет исполняемую команду:
несовпадение завершает граф до выделения рабочего дерева. Для другой команды
повторите привязку рецепта и подготовку плана. Командная оболочка не используется;
метасимволы остаются буквальными аргументами. Команда проверки зависит от проекта
и должна проверять реальные критерии.

В рецептах сохранены выбранные модели, системные инструкции P0, инструменты,
разрешения, схемы вывода, режимы сессий, повторов и исправления вывода.
Планировщик использует `xhigh`, исполнитель — `medium`, ревьюер — `high`;
исполнитель продолжает свою сессию, ревьюер получает новую. Не заменяйте явно
выбранные настройки молча при недоступности модели. Английский текст сохранённых
системных инструкций — часть конфигурации; обычные инструкции задачи и сообщения
рецепта даны по-русски.

## Что означает принятие

После успешной проверки артефакт получает настоящую версию `git-tree:<sha>`.
Ревью связано с этой версией и `acceptanceCriteriaRevision`; обе проверяются
корневым графом. Для C каждый ревьюер должен одобрить ту же текущую версию.
Неуспешная команда и `request_changes`/`inconclusive` возвращают обратную связь
исполнителю. Конкретный `blocked` завершает путь без принятия.
Произвольных лимитов итераций или обязательного этапа согласования нет.

Технический `succeeded` не равен корневому `accepted`. Результат содержит рабочее
дерево с зафиксированным коммитом и доказательства; автоматического слияния нет.
Перед использованием результата проверьте корневой исход, фактическую проверку,
актуальные вердикты, соответствие дерева файлов в коммите и границы изменений.
Рабочее дерево и профиль разрешений инструментов не обеспечивают изоляцию на уровне ОС.

## Вспомогательные скрипты и границы проверки

[snapshot.mjs](snapshot.mjs) копирует реальный индекс выделенного рабочего дерева Git
во временный файл, выполняет `git add --all -- .` и `write-tree`. Исходный индекс
остаётся побайтно неизменным. Учитываются изменения, уже добавленные в индекс и ещё
не добавленные в него, неотслеживаемые файлы вне правил игнорирования, а также
игнорируемые файлы, принудительно добавленные в индекс. Если исходного индекса нет,
временный индекс тоже изначально отсутствует: это соответствует добавлению файлов
в индекс средой исполнения, без подстановки `HEAD`. Связанные рабочие деревья
разрешаются через Git; вложенный рабочий каталог и перечисленные в скрипте
унаследованные переменные, переопределяющие настройки Git, отвергаются. Снимок
описывает Git-артефакт с действующими правилами игнорирования и фильтрации, а не все
файлы компьютера. Скрипт не изолирует внешнюю параллельную запись между снимком,
ревью и коммитом.

[verify-command.mjs](verify-command.mjs) сохраняет реальный код выхода или сигнал
завершения и стандартные потоки вывода и ошибок команды; текст вывода (включая
JSON и TAP) не определяет успех. Для успеха нужны код выхода 0 и одинаковое дерево
файлов до и после проверки. `commandExecuted` отличает ошибку запуска от процесса,
который был запущен и завершился ошибкой. Вывод буферизуется в памяти без
произвольного ограничения `maxBuffer`.

JSON самодостаточны: вспомогательные скрипты встроены в фиксированные аргументы
команды проверки, поэтому исполнители не зависят от пути установки пакета инструкций.
Поддерживаемые исходники вспомогательных скриптов — два файла `.mjs`.
После их изменения обновите все три определения:

```sh
node skills/dynamic-workflows/recipes/implementation-review/embed-helpers.mjs
node --import tsx --test tests/implementation-recipes.test.ts
```

Тест побайтно сравнивает встроенные скрипты с поддерживаемыми исходниками,
проходит официальные операции создания, изменения и компиляции графа, проверяет
маршруты, реальные временные репозитории Git, большие потоки вывода и ошибок,
а также защиту от совпадения путей через символические ссылки. Эти проверки
выполняются без сети и моделей. Для сохранения новой версии как проверенного
пресета нужен её собственный реальный пробный запуск с корневым `accepted`
и актуальными доказательствами.

## Проверяемая привязка commit

S/P/C включают `candidate.expectedTreeFromResult: ["approvedArtifactRevision"]`.
Accepted ребёнок возвращает в этом поле реальный `nodes.snapshot.stdout`, связанный с review;
blocked всегда возвращает null, даже после предыдущего snapshot. Существующий artifactRevision
сохраняется. Успешное исполнение не означает принятие результата.
Runtime журналирует childResult и expectedTree до admission и проверяет Git tree до/после
commit. При drift результат не успешен, правки сохраняются. Уже созданный внешний commit
не отменяется postcheck; гарантия не является sandbox, блокировкой writers или CAS commit-tree.
Старые frozen планы автоматически этот guard не получают.
