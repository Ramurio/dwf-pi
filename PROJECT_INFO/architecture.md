# Архитектура и карта модулей

## Путь задачи

```text
Skill / CLI / MCP → WorkflowService → черновик → проверка → компиляция
                                         ↓ подготовка
                            неизменный ExecutionPlan + preparedId
                                         ↓ запуск
                        RunController → отдельный supervisor
                                         ↓
                         граф Effect → процессы pi/check
                                         ↓
                          журнал SQLite → панель / watch / восстановление
```

Клиенты описывают граф данными; TypeScript + `Effect` генерируется машинно.
Черновик можно редактировать, а план запуска фиксирует граф, конкретные модели,
уровень рассуждений, инструменты, инструкции, `skills`, схемы вывода, исходник и его хеш.
`cwd` канонизируется, но живые файлы и Git `head` подготовка не замораживает.

Управляющий процесс (supervisor) живёт отдельно от вызывающего приложения;
исполнители pi (workers) получают собственные процессы и сессии. SQLite WAL/FULL хранит
владельца, активации узлов, контрольные точки, исходы, ожидания, расход и историю решений.
Панель и watch читают одну проекцию состояния.

## Почему так

- Один сервис CLI/MCP предотвращает разные правила запуска у разных управляющих приложений.
- Неизменный план позволяет проверить, какие инструкции и настройки исполнялись.
  Динамический `map`/цикл меняет число активаций, а не топологию плана.
- Токены владения ограждают журнал от поздних записей старого supervisor.
  Идентичность запуска хранится в журнале, не выводится из пути наблюдателя.
- Пауза прекращает допуск новой работы и дожидается листьев; отмена — отдельное действие.
  Успешные контрольные точки при продолжении не исполняются повторно.
- Одной транзакцией SQLite нельзя гарантировать однократность внешних эффектов:
  после неопределённого результата нужны доказательства и явное разрешение восстановления.
- `worktree` изолирует параллельные изменения Git; `integrate` явно сливает принятые коммиты.
  Конфликт и незафиксированные изменения в целевом дереве не считаются успешным слиянием.
- Ревьюер с новой сессией не наследует переписку исполнителя; `approve` связан с реальной
  `artifactRevision` и версией критериев. Финальный `accepted` задаётся графом.
- Повторы SDK отключены; явная политика повторов учитывает внешние эффекты.
  Исправление формата ответа в той же сессии не равно повтору побочного действия.
- Профили разрешений ограничивают инструменты, но не права ОС. Несколько SDK-сессий
  в общем процессе остаются [экспериментом](development.md#experiments), рабочая реализация
  использует отдельные процессы исполнителей.
