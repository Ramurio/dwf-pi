Статус выполнения и решение о результате — разные данные. `succeeded` означает,
что граф завершился без технической ошибки. Поле `taskOutcome` содержит решение
`accepted`, `rejected`, `inconclusive` или совместимое со старыми запусками
`unclassified`, причину, массив доказательств и источник `explicit` / `legacy`.

## Явное завершение

```json
{
  "id": "done", "kind": "finish", "decision": "accepted",
  "reason": {"op":"literal","value":"Проверки и независимые ревью приняты"},
  "evidence": {"op":"array","items":[{"op":"ref","path":["nodes","checks"]}]},
  "value": {"op":"ref","path":["nodes","artifact"]}
}
```

`finish` заканчивает текущий вызов графа и не имеет исходящих рёбер. `reason` должен
вычислиться в непустую строку, `evidence` — в JSON-массив. `value` возвращается как
обычный выход. Решение корневого графа становится итогом запуска; решения вложенных
графов остаются в метаданных их активаций и не подменяют корневое.
`evidence` хранит объявленные ссылки/результаты. Среда исполнения ещё не доказывает
их применимость к конкретному хешу артефакта: это отдельная работа по артефактам.

Старый `end` продолжает работать: `output.accepted:true/false` даёт совместимые решения
`accepted`/`rejected`, любое другое значение — `unclassified`. Явный `finish` имеет приоритет
над похожими полями внутри выхода. Историческим данным не приписываются новые
доказательства. Пресет сохраняется только после `succeeded` + `accepted`.

## Ожидание как часть графа

```json
{
  "id":"missingEvidence", "kind":"await",
  "reason":{"op":"literal","value":"Нужен результат проверки совместимости"},
  "input":{"op":"ref","path":["nodes","review"]},
  "responseSchema":{
    "type":"object",
    "properties":{"compatible":{"type":"boolean"},"reason":{"type":"string","minLength":1}},
    "required":["compatible","reason"],"additionalProperties":false
  }
}
```

Это иллюстрации узлов, а не целые запускаемые графы: ссылки должны существовать
в авторском графе. `await` имеет обычные исходящие рёбра. Его выход — ответ, проверенный
по зафиксированной JSON Schema без приведения типов/удаления полей. Корневой тип схемы —
`object`; поддерживается тот же строгий набор JSON Schema, что и для выходов исполнителей.
Неверная схема обнаруживается до запуска.

Причина, вход, схема и уникальный ID ожидания сохраняются в SQLite. ID привязан к
запуску, области выполнения, узлу и посещению; повтор восстановления не создаёт новый
запрос, а следующий проход цикла или другой элемент `map` создаёт свой. Когда все
исполняемые листья ждут, запуск имеет статус `waiting`; остальные параллельные ветки
продолжаются. Это не ручная пауза и не обязательное одобрение человеком.

```sh
dynamicwf run.waits <<'JSON'
{"id":"run-RETURNED-ID"}
JSON
dynamicwf run.resolve <<'JSON'
{"id":"run-RETURNED-ID","waitId":"wait-RETURNED-ID","response":{"compatible":false,"reason":"Не совпадает формат"},"resolvedBy":"agent"}
JSON
```

MCP: `run_waits` и `run_resolve` с теми же полями. `resolvedBy` — описательная метка
клиента, не аутентифицированная личность. В браузере раздел «Сейчас» показывает причину,
вход и схему, JSON-форму и ошибку проверки. При обновлении данных и переходе между
вкладками черновик сохраняется в памяти страницы. Полная перезагрузка его пока не сохраняет.

Ответ и событие `wait.resolved` фиксируются одной транзакцией. Повтор того же ответа
идемпотентен, конфликтующий ответ отклоняется; первая метка источника сохраняется.
Нельзя ответить на новый запрос уже завершённого/отменяемого запуска. Исторические
незакрытые запросы остаются видны API после отмены, но больше не принимают ответ.

После создания продолжения через `run.continue` исходный запуск также не принимает
новый ответ: проверка выполняется в транзакции до изменения ожидания и записи события.
Повтор уже сохранённого одинакового ответа остаётся идемпотентным и не запускает
заменённый процесс. Ответить на открытое ожидание источника нужно до создания
продолжения; новые ожидания принадлежат уже запуску-продолжению.

## Пауза, смерть процесса и восстановление

Ручная пауза может завершиться при активном `await`: в нём нет исполняющегося работника.
Ответ разрешено сохранить на паузе; выполнение продолжится после `run.resume`.
Продолжение без ответа не разрешает ожидание. При подтверждённой смерти supervisor
сервис может запустить тот же граф при `run.resolve`, сохранив ID ожидания и завершённые
контрольные точки. Просто закрытое управляющее приложение не требует восстановления.

`worktree` в фазе `children` повторно подключается после проверки принадлежности ветки/
пути/репозитория, Git-состояния и `base`. Завершённые дочерние записи не повторяются,
незакоммиченные файлы сохраняются. Это разрешение не распространяется на неопределённый
результат дочернего `agent`/`check` или прерванное выделение дерева/создание коммита.
Тогда по-прежнему требуется явное разрешение восстановления; `run.resolve` его не заменяет.

`finish`/`await` доступны начиная с версии компилятора/среды исполнения v2, запись переходов —
с v3. [План](execution-plan.md) описывает актуальную версию и совместимость.
V1 запрещает `finish`/`await`; старым планам не приписываются новые исходники/хеши или
отсутствовавшие записи переходов. `schemaVersion` графа остаётся 1. Адресуемая подготовка
уже реализована: [снимок и идемпотентный запуск](execution-plan.md#prepared-start).

## Проверки

`tests/await-outcome.test.ts` исполняет отдельные процессы без моделей: явные решения,
запрет сохранения непринятого пресета, эталонный план v1, принудительный SIGKILL и новый
сервис, ошибку схемы/повтор ответа, паузу→ответ→продолжение, независимые ожидания `map`,
отмену, повторное подключение `worktree`, корневые/дочерние исходы и API браузера с условными
переходами. `tests/run-store.test.ts` проверяет защиту владения и откат ответа при ошибке
записи события.

Пример для ручной проверки в браузере:

```sh
node --import tsx spikes/ui-await-smoke.ts
```

Откройте напечатанную ссылку, проверьте неверный тип, исправьте ответ, поставьте паузу,
сохраните ответ и продолжите. Ctrl+C отменяет незавершённый проверочный запуск,
дожидается остановки процессов и удаляет только его временные данные.

## Сбор независимых ветвей: `collect`

`parallel` и `map` принимают `failurePolicy:"collect"`. Значение по умолчанию либо
явно заданный `fail-fast` сохраняет обычное распространение ошибок `Effect` и выходы
без оболочек. Политика фиксируется в плане начиная с v5; параллелизм независим,
без скрытого ограничения.

```json
{"status":"succeeded","value":{"decision":"request_changes"}}
```

```json
{"status":"failed","failure":{"version":1,"code":"provider","phase":"execution","effects":"unknown","message":"Pi assistant turn failed or was aborted"}}
```

`parallel` возвращает объект по ID детей, `map` — массив в **исходном порядке**, независимо
от порядка завершения. `request_changes`/`inconclusive` и обычный ненулевой выход `check`
остаются успешными значениями исполнения. Инфраструктурный отказ не превращается
в голос ревьюера. Вложенный `collect` сохраняет вложенные оболочки. `collect` не задаёт
повтор/кворум/приёмку: следующие узлы явно решают, ждать, повторять по политике,
отклонять или принимать.

Сначала проверьте `nodes.council.correctness.status`, затем читайте `value.decision`
либо `failure` соответствующего случая. Строгие выражения не подставляют отсутствующие значения.

### Границы ошибок и управления

Собирается только обычный типизированный канал ошибок дочернего эффекта **после
завершения финализаторов**, включая ошибку вычисления входа дочерней ветви `parallel`.
Невалидный `map.items` проваливает родителя до создания элементов. Дефекты/прерывание `Effect`
и типизированные `cancelled`/`interrupted`/`uncertain-effect` продолжают прерывать выполнение,
даже смешанные с обычными ошибками в составной причине. Ошибка очистки также распространяется:
завершение не подтверждено. Ошибка записи контрольной точки коллекции не превращается
в выдуманную ошибку ребёнка; устаревший владелец не может зафиксировать результат.

Причина сохраняется, но эффекты на уровне ветви консервативно `unknown`: её предыдущий
узел мог писать до отказа узла только для чтения. Активации листьев сохраняют более
точные факты. Из нескольких обычных составных причин оболочка содержит первую,
индивидуальные активации — свои. `collect` не откатывает раннюю работу и не разрешает
неопределённый повтор. Неудачный ребёнок не отменяет независимых соседей; `await` остаётся
ожиданием, пауза закрывает новый допуск и дожидается принятой работы. Отмена прерывает
запуск, а не становится успехом.

### Идентичность и восстановление коллекции

`workflow_collections` хранит результат ребёнка под ID запуска + ключом родительской
активации (область/посещение) + ID элемента. `parallel` использует авторский ID ребёнка;
`map` — нулевой индекс строкой. Сохраняются `seq`/время и исходная **родительская** попытка.

Результат, родительская `metadata.collectionSummary` и событие collection.settled атомарны
и защищены проверкой владельца. Идентичная повторная доставка возвращает запись,
конфликт отвергается. После восстановления завершённый ребёнок возвращает сохранённую
оболочку без входа во вложенный граф, сохраняя и успехи, и ошибки. Смена родительской
попытки не сбрасывает детей; новое посещение графа имеет другой ключ и свою коллекцию.

Авария после ошибки ребёнка с внешними эффектами, но до фиксации коллекции не позволяет
выдумать исход: допуск по-прежнему запрещает неопределённый повтор, требуется явное
восстановление. Результаты завершённых дочерних узлов можно прочитать из контрольных
точек, чтобы заполнить недостающую запись успешного результата коллекции, не повторяя
их работу. Расход остаётся на исходных активациях листьев/попытках; чтение коллекции
из журнала не добавляет токены, её оболочки/сводка не являются отчётами исполнителя.

### Инспекция и проверки `collect`

`run.collections {"id":"run-...","key":"parent-activation-key","after":0,"limit":100}`
(MCP run_collections) листает неизменяемые результаты в порядке завершения/фиксации.
Ключ берите из `run.inspect`. Ответ: `enabled`, `summary`(`total`/`succeeded`/`failed`), `records`,
`nextAfter`, `hasMore`. Сводка всей коллекции и страница читаются одним снимком SQLite.
Неизвестная активация — ошибка; для других узлов явно `enabled`:`false`. Размер страницы
ограничивает ответ API, не исполнение.

Родитель в браузере показывает политику/сводку; «Результаты веток» раскрывает значения/
ошибки с исходными попытками. Страницы переживают перерисовку/смену запуска и обновляются
явно. История watch показывает собранные ошибки даже у успешного родителя, поток
изменений — изменения счётчиков. Взаимодействие с повторами — в [политике](retry-and-failures.md#retry).

Исходники/хеши v1–v4 сохранены, заданный автором `failurePolicy` ими отвергается; эталонный
v4 по-прежнему даёт обычные значения. [Таблица версий](execution-plan.md#versions).
`tests/collection.test.ts`, `tests/campaign-collect.test.ts`, `tests/wave5-crash-collect.test.ts`
используют отдельные управляющие процессы, команды и ожидания без моделей: неудачную
запись рядом с завершёнными/ожидающими соседями, SIGKILL без повторения записи, отмену,
`fail-fast` по умолчанию, упорядоченные/вложенные результаты, ошибки входа, управления,
очистки и дефекты, откат/защиту владельца/дедупликацию/конфликты/страницы и API.
Ручной пример: `node --import tsx spikes/ui-collection-smoke.ts`.
