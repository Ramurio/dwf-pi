# Наблюдение: браузер, терминал, трасса и расход

[Индекс](README.md) · [CLI/MCP](service.md) · [Журнал](run-journal.md)

Все интерфейсы читают общий журнал и одну проекцию контроллера. Структура графа,
решение маршрутизации, допуск узла и приёмка задачи — разные факты.

Оглавление: [проекция](#projection) · [браузер](#browser-ui) · [терминал](#watch) ·
[трасса](#routing-trace) · [расход](#usage).

<a id="projection"></a>
## Общее представление запуска

`RunController.snapshot`(`id`) сначала проверяет известные процессы через `observe`, затем
получает активации и строит `projectRun` из `src/observation.ts`. Результат используют
сервис/CLI/MCP, список/детали запусков в браузере, интерактивный watch и его поток
изменений. Наблюдение не перезапускает граф; подтверждённая смерть supervisor и
исполнителей фиксируется как `interrupted` тем же механизмом контроллера.

`presentation` содержит:

- `status`, `desired`, `statusLabel`, `terminal` — выполнение и намерение оператора.
- `taskOutcome`, `outcomeLabel`, `accepted` — приёмку с общей совместимостью старых данных.
- `activeKeys` — конкретные исполняемые задачи; ожидания и контейнеры с активными детьми
  не удваивают счётчик. На `paused`/`interrupted`/конечном состоянии активных задач 0.
- `waitingKeys` — активации `await`, сейчас ждущие ответа. Исторические незакрытые запросы
  после прерывания/отмены отдельно доступны через `run.waits`.
- `liveness` — состояние, подпись, факт присутствия supervisor, число живых исполнителей
  и время проверки процессов.

| `liveness` | Значение |
| --- | --- |
| `supervised` | Найден supervisor с ожидаемой идентичностью |
| `orphaned-workers` | Supervisor не найден, но записанные исполнители ещё живы |
| `unresolved-groups` | Исполнитель не найден, но в записанной группе есть процессы; принадлежность требует проверки |
| `launching` | Есть резервирование без подтверждённого PID, смерть не установлена |
| `stopped` | Проверка не обнаружила процессы запуска |
| `unknown` | Проекция построена без проверки ОС; флаги и время равны `null` |

Устаревший heartbeat не переводит запуск в `interrupted`. Конечный исход также не
доказывает отсутствие процессов. Проверка ОС и чтение SQLite — последовательные
наблюдения, не общая атомарная транзакция; следующий опрос уточняет состояние.
При ошибке проверки ОС клиент получает ошибку, не выдуманный `stopped`. Защитные токены
владельца/исполнителя в `presentation` не входят.

Резервирование до PID и неразрешённые группы проверяются по
[протоколу восстановления](reconciliation.md#groups). `unresolvedGroupProcesses` считает
кандидатов отдельно от `workersAlive`, не выдавая их за подтверждённых исполнителей.

Браузер получает готовые подписи статуса/результата/живости; список запусков показывает
приёмку после завершения. Время проверки не входит в признак изменения отображения,
поэтому опрос без смысловых изменений не закрывает доказательства и не пересоздаёт
форму. При смысловом обновлении раскрытие блоков сохраняется по контексту запуска,
графа, области, активации и попытки; раскрытие данных ожидания — по его ID;
редактируемый ответ удерживает текст, фокус, направление выделения и прокрутку поля.
Терминальный поток изменений тоже не печатает строки из-за часов. Ожидающие
запросы показывают причину и ID ожидания. Структурные записи на паузе видны как контекст
продолжения, но не считаются работающими задачами.

`tests/observation.test.ts` проверяет матрицу процессов/приёмки/паузы и соответствие
проекций; `tests/await-outcome.test.ts` — watch как первого наблюдателя после SIGKILL,
совпадение сервиса и списка/снимка браузера на реальном ожидании. Оптимизация
чтения/проверки множества процессов остаётся отдельным направлением.

Активная работа индексируется по точным сегментам `scope` и номеру `visit`:
соседние имена и похожие строковые префиксы не считаются вложенностью. Контейнер
с работающим потомком или потомком с запланированным повтором не удваивает счётчик.
Стоимость индексации без разбора метаданных повтора — `O(N + S + P)`, где N — число
записей, S — сумма длин индексируемых `scope`, P — сумма длин проверяемых префиксов. `active-work-index`
сравнивает результат с независимым эталоном и считает операции при разных размерах
входа. Этот индекс не меняет правила допуска повторов.

<a id="browser-ui"></a>
## Браузерная панель

Постоянная закладка по умолчанию: **http://127.0.0.1:4380/**.
Панель показывает старые и новые запуски из общей базы dynamicwf.

```sh
# Один раз на macOS: включить запуск панели при входе в систему и запустить её сейчас
dynamicwf ui --install
# Открыть/найти панель без настройки автозапуска:
dynamicwf ui
# Получить сохраняемую ссылку на конкретный запуск:
dynamicwf ui --run <run-id>
# Выбрать другую базу/порт при первоначальной настройке:
dynamicwf ui --install --store /path/to/state.sqlite --port 4380
# Отключить автозапуск и остановить только панель:
dynamicwf ui --uninstall
# Временный независимый просмотрщик (другая база, случайный порт, Ctrl+C для выхода):
dynamicwf ui --foreground --store /path/to/other.sqlite --port 0
```

Обычная команда печатает ссылку и завершается. Сервер работает в фоне; повторная
команда использует уже работающий экземпляр. Dynamicwf `graph` — альтернативное имя
той же команды. База и порт сохраняются в `~/.dynamicwf/dashboard/config.json`;
без явных параметров используются сохранённые настройки, при первой настройке —
общая база и порт 4380. Если панель уже работает с другой базой/портом, команда объясняет
конфликт: сначала --uninstall, затем новая настройка, либо отдельный --foreground.
Занятый другим приложением порт не подменяется случайным.

На macOS --install создаёт пользовательский LaunchAgent: поднимает панель при входе
и восстанавливает после падения. Исходный каталог проекта и Node должны оставаться
доступны; после переноса выполните --uninstall, затем --install из новой установки.
Лог сервера: `~/.dynamicwf/dashboard/server.log`. На других ОС доступен фоновый режим;
установка автозапуска пока реализована только для macOS.

Старая ссылка `http://127.0.0.1:4380/?run=<id>` открывает обзор запуска. При навигации
адрес также сохраняет `view`, `graph`, `scope`, `node`, `activation` (ключ журнала)
и `attempt`. Перезагрузка и назад/вперёд восстанавливают конкретную попытку, в том числе
архивную. Ключ активации определяет граф/узел/область даже при устаревших подсказках
в URL. Отсутствующий запуск или выбранный граф обозначается явно, без подмены другим
графом; выбор существующего графа/области в списке сразу снимает сообщение о недоступном
контексте даже без нового события журнала. Переход к выполнению другого запуска добавляет
одну запись истории (без промежуточной страницы запуска). Быстрое повторное «Назад» во
время загрузки сохраняет последнюю выбранную ссылку. Закрытие
вкладки/терминала или перезапуск панели не отменяет графы: их исполнением управляют
отдельные процессы supervisor.

### Рабочее пространство

Слева — задачи и их запуски, ниже — раскрываемые этапы текущего графа. Группировка
использует только `lineage.taskId`; совпадение названия, каталога или времени не связывает
старые независимые запуски. Внутри этапа видны конкретные проходы/попытки и вызванные
ветки. Вложенность определяется сегментами `scope`, включая проход родителя;
идентификаторы, совпадающие с именами маркеров `node`/`visit`/`parallel`/`map`,
остаются значениями, а не новыми сегментами. При выборе одного вызова статус
в дереве и графе относится только к точной области; общий статус виден при «Все вызовы».
Хлебные крошки возвращают в конкретный родительский вызов.

Вверху — компактный итог или требуемое действие, статус и управление. План, хеши,
результат, доказательства, живость и восстановление находятся в раскрываемых сведениях.
Граф занимает основную область первого экрана; инспектор появляется после выбора.
На узких экранах он открывается поверх правой части и закрывается кнопкой.

- **Обзор:** схема, дерево и последние 20 выполнений выбранной области с переходом
  ко всей последовательности. Колесо и кнопки меняют масштаб, перетаскивание фона
  перемещает схему; при фокусе на схеме работают стрелки, `+`/`-` и `Home` («Вместить»).
  Масштаб сохраняется при открытии инспектора и изменении размера окна.
- **Работа и ответы:** активные задачи, последнее событие pi и ожидания. Контейнеры
  не удваивают число работающих детей. Ожидание показывает причину, ID, вход, схему
  и JSON-форму с серверной проверкой. На паузе ответ сохраняется до «Продолжить».
  После отмены или создания продолжения показана причина ограничения и ссылка на новый запуск.
- **Последовательность:** проходы в порядке первого допуска, фильтры агентов и ошибок/
  замечаний, результат, попытки и сохранённые причины переходов рядом с выполнением.
  Фильтр «Ошибки и замечания» включает сохранённые `findings`, даже если краткий результат
  ревью не содержит слов `request_changes` и технический статус — `succeeded`;
  наличие замечаний само по себе не назначает вердикт ревью. Смена фильтра
  с клавиатуры сохраняет фокус на том же элементе управления и доступную
  позицию прокрутки.
  Сначала отображаются 100 записей; кнопка открывает следующие 100 с явным счётчиком.
  Это пагинация представления, не ограничение исполнения или хранения.
- **Переходы:** полная страничная трасса, условия и выбор каждого ребра, источник на графе.
  В последовательности и инспекторе доступна та же загрузка причин переходов.
- **Расход:** запуск или вся связанная задача, детализация моделей и ответов, полнота,
  кэш, рассуждения и оценка SDK. Страницы сохраняются при переключениях. Строка отчёта
  открывает исходный запуск/ключ/попытку производителя, включая источники продолжения.
  `reuse` не приписывает себе вызов модели. [Семантика учёта](#usage).
- **Инспектор:** определение этапа отдельно от конкретного выполнения. Для выбранного
  прохода структурного узла доступны ссылки на записанные дочерние области этого
  прохода; отдельная кнопка «Схема · все вызовы» намеренно снимает выбор конкретного
  выполнения. У архивной попытки связь с дочерним вызовом не предполагается: дерево
  скрывает ссылки на дочерние вызовы последней попытки и предлагает явную схему всех
  вызовов. Сводка расхода выполнения на выбранной последней попытке накоплена за *все*
  попытки; расход каждой сохранённой попытки отдельно указан в карточках попыток.
  Строки истории и активности и статусы блоков графа показывают *последнее* состояние;
  при выборе архива они не выделяются как строки выбранной попытки. Доступны
  выход, замечания, ошибки, расход, переходы, архивные попытки, политика повторов,
  результаты веток, ремонт вывода и существующие действия восстановления.
  Архивная попытка закреплена в URL и не заменяется последней при опросе;
  если её страница не загружена или запись отсутствует, это указано явно.
  Если попытка становится архивной во время опроса, страница попыток загружается
  без вложенной перерисовки инспектора, в том числе когда она уже была открыта для
  прежней текущей попытки. Её живой снимок не служит архивной записью: архив читается
  из журнала по курсору; при задержке/ошибке показывается отсутствие подтверждённых
  данных, а не старый результат. Если страница попыток опережает общий снимок,
  интерфейс ждёт его обновления без бесконечного повторного чтения. Раскрытие, фокус,
  прокрутка и одна строка выполнения сохраняются до и после ответа.
  Закрытие инспектора переводит фокус к видимому поиску запусков на вкладках вне обзора,
  а в обзоре — к кнопке размещения графа.
- Пауза, продолжение и отмена проходят через `RunController`. Подтверждение отмены
  связано с названием/ID и текущим посещением запуска: переключение, включая «Назад»,
  закрывает диалог. Поздний ответ команды не переносит ошибку на новый запуск.

Подпись этапа берётся из необязательного авторского `label`; старый план показывает ID
и тип/роль. Из скрытого задания агента назначение не угадывается. Имена и причины
выводятся как текст. Новый `label` входит в зафиксированный план; старые планы и хеши
не переписываются. Исполнение графа от этой метаинформации не меняется.

Схема показывает возможные переходы; подсветка пройденных рёбер берётся из сохранённой
трассы выбранной области. Структура сама не доказывает выполнение ветки. Цвет блока
отражает журнал, записанные `findings` и непринятый результат выделяются отдельно,
не превращая технический успех в приёмку. У повторявшегося узла учитывается последний
результат каждой ветки, история сохраняет прошлые проходы.
Выбор, раскрытие дерева/деталей, прокрутка, фокус хлебных крошек и черновики форм
сохраняются при обновлении. Автоматическое чтение хвоста трассы после нового снимка
не заменяет раскрытия, фокус и прокрутку до завершения чтения. При ширине до 700 CSS px
панель складывает боковую колонку над содержимым и включает прокрутку страницы, в том
числе при увеличении масштаба браузера. Локальная память различает запуск, граф,
область, ключ и попытку;
навигация не переносит раскрытие другой попытки по позиции в списке. URL восстанавливает
выбранный контекст после перезагрузки; масштаб, раскрытие и несохранённые черновики
хранятся только в памяти вкладки и полной перезагрузки не переживают.

Снимок дополнен `activation.order`: номера событий первого/последнего допуска,
попытка и номер решения перехода. Индекс читается инкрементально из существующих
`activation.started`/`route.decided`, без новой записи в журнал и без копирования
приватных payload. При отсутствии индекса история использует время как запасной
порядок, но не доказывает причинность по совпадению времени. Ссылка «Открыть следующий проход» требует сохранённого решения и более позднего допуска
его цели в том же графе и точной области. До загрузки трассы причина обозначена как
незагруженная; отсутствие допуска не выдаётся за выполненный переход. Старые v1/v2
без трассы не получают выдуманных причин.

Снимок обновляется примерно раз в секунду, список — раз в три опроса. Проверка выбранного
запуска использует ту же сверку живости/прерывания, что `run.status`. Отсутствие события
модели не доказывает зависание. Журнал, редактирование CLI/MCP, пресеты и исполнение
сохраняют интерфейсы; браузер служит наблюдению/управлению существующими запусками.

Параллельные чтения снимка привязаны к текущему выбору запуска и порядку запросов.
Опрос без смысловых изменений не пересоздаёт дерево: его существующие кнопки и крошки
остаются рабочими, хотя объект снимка после декодирования заменяется. При переходе к чужому выполнению выбранные ключ и попытка ждут *принятого* снимка:
если первый ответ обогнал новый опрос и был отброшен, следующий актуальный снимок
завершит переход. Пока новый запуск загружается или недоступен, старое дерево скрыто,
а его сохранённые обработчики недействительны. Запоздавший ответ или отказ не возвращает
старую форму, статус или ошибку связи;
устаревший 401 не перезагружает страницу с уже актуальной сессией. Переключение
туда и обратно также не возвращает состояние прежнего посещения. Это защита
от устаревшего отображения, а разрешение управляющего действия проверяет сервер.

Это правило распространяется и на фоновые страницы истории, расхода, попыток
и восстановления: их старый 401 не перезагружает другое посещение запуска.
При этом данные и ошибки остаются в исходном кэше. Запоздавшие завершения POST
ответа ожидания и чтения расхода задачи не перерисовывают новый визит A,
пока его снимок не загружен. Если он уже загружен и показывает то же ожидание,
страница снимает состояние «Сохраняем…» и выводит ответ сервера или ошибку
первой отправки; POST автоматически не повторяется. Чтение страницы трассы
или расхода тоже обновляет видимый новый визит при совпадении запуска и
отображаемого ресурса, включая историю, инспектор и расход всей задачи. Старый
401 не перезагружает новый визит, но фиксирует ошибку исходной страницы. Квитанция сохранённого решения
о восстановлении и его `decisionId` сохраняются независимо от навигации; поздняя
квитанция не меняет сообщение нового посещения и не начинает для него чтение.
Актуальный 401 по-прежнему восстанавливает доступ к панели. Позднее чтение попыток,
результатов веток, повторов или инспекции/решений восстановления при A → B → A не
перерисовывает инспектор до приёма нового снимка A. Если снимок уже принят и показывает
*тот же ключ* выполнения, завершение старого GET сразу обновляет страницу и кнопку
загрузки даже без нового события журнала; другое выполнение не перерисовывается.
Ответ или ошибка остаются в кэше исходного ресурса. Квитанция POST сохраняется даже при такой навигации, не меняя
сообщение нового посещения. Отправленные ответы ожиданиям и решения восстановления
автоматически не повторяются.

Выбранный узел графа сообщает состояние через `aria-pressed`, а SVG-заголовок
содержит полное имя и идентификатор узла как текст. Выбор мышью, Enter и пробелом
использует прежние обработчики. `graph-node-accessibility` проверяет состояние,
текст заголовка и настоящее нажатие пробела в отдельном окружении Chrome
без прокрутки страницы; пропуск браузерного случая не считается его исполнением.

### Локальная граница

Сервер слушает только 127.0.0.1, проверяет точный Host и не включает CORS. Открытие
страницы в отдельной вкладке создаёт cookie с HttpOnly/SameSite=Strict; ключ не попадает
в ссылку. Встраивание в чужую страницу запрещено. Запросы других сайтов/локальных
источников отклоняются по Fetch `metadata`/Origin. Управляющие POST дополнительно требуют
cookie, тот же Origin, JSON и специальный заголовок. После перезапуска сервера браузер
автоматически обновляет страницу и получает новую сессию по прежнему адресу.
Другие локальные процессы с правами пользователя остаются в доверенной границе:
это не защита от вредоносного ПО на компьютере.

У CLI отдельный секрет в приватном каталоге настроек: только для проверки экземпляра
и остановки панели, браузеру не передаётся. Секреты графов не меняются. Временный
--foreground сохраняет случайный ключ в пути URL. Страница не загружает внешние ресурсы;
CSP запрещает внешние скрипты/встраивание. Обычный снимок не отдаёт токены владельца/
исполнителя, инструкции, учётные данные, пути сессий или сырые логи. Явные API попыток/
восстановления раскрывают записанные `task`/`input` операции и пути по запросу; файлы сессий
не читают. Названия, условия, результаты и замечания отображаются текстом, без исполнения HTML.

<a id="watch"></a>
## Терминальный монитор

```sh
dynamicwf watch --run run-…
dynamicwf watch --run run-… --store /path/to/state.sqlite
```

По умолчанию открывается компактный экран **Сейчас**: один экран терминала, обновление
на месте без копий графа в истории. Размер подстраивается под окно; длинные строки
обрезаются, содержимое прокручивается.

- **1 — Сейчас:** задачи, длительность, модель/`thinking`, последнее событие исполнителя,
  пять последних завершённых задач и возможные следующие переходы.
- **2 — История:** завершённые задачи, новые сверху; решения ревьюеров, коды проверок,
  ошибки, отдельные проходы/попытки восстановления.
- **3 — Схема:** графы, узлы, связи и суммарные токены `agent`-узлов. При связанной задаче/
  продолжении строка `task`/Continuation показывает связь, не запуская работу.
- **4 — Токены:** вход/выход/итог, расход/доля моделей, агенты/проходы по расходу.
- **↑/↓**, **j/k**, **PageUp/PageDown**, **Home** — прокрутка выбранной вкладки.
- **q / Ctrl+C** — закрыть монитор; граф продолжит работу.

Завершённый запуск остаётся на экране для изучения истории. Выход возвращает предыдущий
экран и обычный режим ввода. Монитор не отправляет pause/`resume`/`cancel` и не меняет владельца.

### Как читать экран

`candidate #1 / council #2 / correctness / review · проход 1` означает первое рабочее
дерево, второй вызов совета и ветку `correctness`. Проход 2 самого узла — повторное
посещение в той же ветке; попытка 2 — восстановление того же прохода. Элементы `map`
нумеруются с единицы. Ветки сохраняют имена, поэтому ревьюеры не выглядят одинаковыми строками.

Контейнеры `worktree`/`parallel`/`map` скрыты из текущей работы при работающих детях.
При выделении/завершении дерева или на паузе контейнер может показываться отдельно.
Счётчик включает реально работающий этап дерева, но не ожидающие контейнеры и `await`;
на завершённой ручной паузе равен 0.

Длительность обновляется по часам. Последняя активность — событие журнала pi: начало
запроса, ожидание ответа, инструмент, завершение хода. Это не поток рассуждений модели;
отсутствие событий не доказывает зависание. Watch использует ту же проверку процессов/
проекцию, что `run.status` и браузер. После подтверждённой смерти supervisor/исполнителей
пишет `interrupted` вместо устаревшего `running`. Неподтверждённый запуск supervisor и
живые исполнители без supervisor различаются. Heartbeat не доказывает жизнь или смерть.
Закрытие watch только отключает просмотр.

Успех узла не означает одобрение продукта: `request_changes`, `inconclusive`, ненулевой
код выхода и `accepted`:`false` показаны явно. Итог берётся из общей `taskOutcome` с чтением
`accepted` старого `end`. Заголовок отмечает `rejected`/`inconclusive`/`unclassified` при
техническом `succeeded`. `await` показывает причину/ID, в том числе в потоке изменений.

Ожидающий повтор показывает полную идентичность активации — граф, узел, `scope` и
`visit` — и переход между номерами попыток. `delayMs` берётся из сохранённого решения;
`dueAt` выводится как Unix-время в миллисекундах либо `null`. Управляющие символы
в именах экранируются. Полный и краткий вывод показывают повтор только для текущей
неуспешной попытки с решением `scheduled`; завершённый запуск не показывает
устаревшее ожидание. Регрессия: `terminal-retries`.

### Снимки и вывод в файл

```sh
dynamicwf watch --run run-… --once          # компактный снимок
dynamicwf watch --run run-… --graph --once # полная техническая схема
dynamicwf watch --run run-… --plain        # только изменения, без перерисовки
```

При перенаправлении stdout поток изменений включается автоматически. Сначала текущие
задачи и до пяти недавних результатов, затем только новые переходы статусов.
Heartbeat/повторные опросы не дублируют строки. После завершения такой монитор выходит
автоматически. Полная история остаётся на вкладке 2 и в `run.events`; короткие состояния
между опросами могут не попасть в текстовый поток.

Хранилище по умолчанию — `$DYNAMICWF_HOME/state.sqlite`, иначе `~/.dynamicwf/state.sqlite`.
--store должен совпасть с запуском. Текст графа очищается от управляющих кодов,
ANSI и последовательностей изменения направления письма.

`tests/monitor.test.ts`, `tests/terminal.test.ts`, `tests/setup.test.ts` проверяют
проекцию, размеры, очистку символов и CLI. Дополнительная проверка псевдотерминала

### Как читать токены на экране

`Токены: 342 134 · отчётов: 5/5` — пример сохранённых счётчиков пяти исполнителей,
не обещание расхода. Повторно переданный контекст учитывается снова. История показывает
проход, схема суммирует все проходы/ветки `agent`-узла; контейнеры и скопированные
результаты детей не считаются второй раз. Неполнота, кэш/рассуждения и стоимость SDK
трактуются по [общему контракту](#usage).

<a id="routing-trace"></a>
## Фактическая маршрутизация

Планы с версии компилятора/среды v3 записывают выбор после каждого завершённого
нетерминального узла. `runtime.route` вычисляет условия в авторском порядке, сохраняет
результат и только затем возвращает следующую позицию исполнения. `end`/`finish` завершают
вызов без исходящего перехода. Выбранное ребро — решение планировщика; старт цели
подтверждается отдельной активацией.

`RoutingDecision` версии 1 содержит исходный узел, выбранный `edgeIndex`/цель либо ошибку,
причину `condition`/`fallback`/`no-match`/`error` и результат каждого исходящего ребра:
`true`/`false`/`not-evaluated`/`fallback`/`error`. Первое `true` прекращает проверку, остальные
остаются `not-evaluated`. Запасной переход применяется после всех `false` независимо
от позиции. Неверный тип/отсутствующая ссылка прекращает маршрутизацию, не выбирает `fallback`.

Индекс ребра — нулевой индекс в `graphs[graphId].edges` зафиксированного плана.
Браузерное «ребро #N» показывает индекс + 1. Номер исходящего перехода на подписи —
отдельный локальный порядок узла. Полная идентичность решения: запуск + ключ активации
(`scope`, `graph`, node, `visit`). Динамические вызовы `map`/`parallel` не смешиваются даже при
одинаковых ID/`visit`. Запись содержит попытку исходной активации, время, курсор и решение.
Все значения входа/контекста в трассу не копируются; условие сопоставляется с
зафиксированным AST и выходами `run.inspect`.

Выбор перехода и его объяснение используют общую логику. Сохранены версия трассы
`v1`, глобальные индексы рёбер, порядок и короткое замыкание условий. Ошибка
вычисления передаётся как исходное брошенное значение; JSON-трасса содержит её
описание. Регрессия `routing-equivalence` проверяет совпадение выбора и объяснения,
включая разные цели переходов и ошибки.

### Журнал и восстановление

`workflow_transitions` хранит одну запись на исходную активацию; запись и route.decided
атомарны. Токен владельца обязателен; одинаковый повтор не добавляет запись,
конфликтующий отвергается. После восстановления используется сохранённый переход
без повторного вычисления.

При смерти supervisor между точкой исходного узла и записью перехода планировщик
восстанавливает выходы из точек, вычисляет переход и записывает его. Завершённое
внешнее действие не повторяется. Если условие упало, исходная активация может быть
`succeeded`, а запуск `failed`: разные факты сохраняются оба.

V1/v2 запускаются с исходными байтами/хешами и прежним `chooseEdge`. API возвращает
`summary.supported`:`false`; причины старых переходов не восстанавливаются из цветов/
порядка активаций. Снимок старого запуска также не получает вымышленные рёбра.

### API и браузер

```sh
dynamicwf run.trace <<'JSON'
{"id":"run-RETURNED-ID","after":0,"limit":100}
JSON
```

MCP run_trace принимает те же поля. Ответ: `planHash`, `summary`, `records`, `nextAfter`, `hasMore`.
Курсор исключает уже прочитанное; страницы 1–1000 записей. Неизвестный ID и неверный курсор —
ошибки. Сводка считает все сохранённые решения, ошибки и выборы рёбер по графу/области.
Чтение не меняет журнал и не запускает восстановление.

«Переходы» показывают решения в порядке записи, условия/результаты. Страницы сохраняются
при смене запуска/вкладки; просмотр подхватывает новые записи после прочитанного хвоста.
«Показать источник на графе» выбирает граф/область/исходный узел, перемещает камеру
и показывает решение в деталях. Зелёные связи имеют записанный выбор в текущей области,
синяя относится к выбранной записи. Счётчики в SVG title доступны без трактовки цвета.

`no-match` в трассе означает отсутствие подходящего условия *и* запасного перехода;
это не использование `fallback`. Переход из ошибочной ссылки с отсутствующим графом
к записанному источнику трассы сверяет новый контекст и снимает прежнее предупреждение
до следующего опроса.
Серые/непосещённые узлы не получают `skipped` лишь из-за отсутствия активации. Сравнение
артефактов и версии критериев остаются отдельными этапами.
Трасса объясняет условие, не доказывает качество политики.

### Проверка

`tests/routing-trace.test.ts`: приоритет условий/запасной переход/короткое замыкание,
строгие ошибки, реальный цикл, SIGKILL и восстановление без повторных записей/действий,
окно между действием и точкой перехода, области `map`, страницы, соответствие API/счётчиков,
атомарность с намеренным отказом события и исходный эталонный v2. Эталонный v1 остаётся

<a id="usage"></a>
## Учёт расхода

Исполнители отправляют `usage.report` после message_end каждого ответа модели,
до проверки submit_result, привязки ревью и итоговой контрольной точки. Записи
сохраняются в отдельном учётном журнале SQLite.

Идентичность: запуск + активация + попытка + `reportId`. Идентичная доставка идемпотентна,
конфликтующее содержимое того же ID отвергается. Запись, агрегат и `usage.reported`
фиксируются одной транзакцией с проверкой владельца supervisor. Следующая попытка
имеет отдельное пространство ID отчётов; следующее посещение — отдельную активацию.

Сохраняются `input`, `output`, итог провайдера, `cacheRead`/`cacheWrite`, `reasoning` при наличии
и стоимость SDK. Рассуждения входят в `output`. Не выводите `total` сложением частичных
полей разных провайдеров. Неизвестная детализация остаётся неизвестной. Сессия индексируется
при создании, поэтому её можно найти и после невалидного ответа.

Если детализация есть только у части ответов, сохраняются известная сумма и `partialFields`
с именами неполных полей. В сводке независимы `cacheReadPartial`/`cacheWritePartial`/
`reasoningPartial`/`costPartial` и число активаций, сообщивших поля. Полный `total` не означает
полную детализацию. Полностью отсутствующее поле не становится известным нулём.

`usage.settled` сообщает полноту независимо от успеха задачи. Завершённый ответ с неверным
результатом может иметь полный учёт; отменённый поток оставляет неполный учёт, сохраняя
полученные числа. Жёсткое завершение процесса не восстанавливает несообщённый расход.

```sh
dynamicwf run.usage <<'JSON'
{"id":"run-ID","after":0,"limit":100}
JSON
```

Ответ содержит `summary`, `reports`, `nextAfter`, `hasMore`. Передайте `nextAfter` как after
для следующей страницы. Размер 1–1000 ограничивает ответ API, не бюджет графа.
CLI/MCP имеют один контракт. Браузерная вкладка «Расход» даёт такую же страницу числовых
отчётов. Раскрытые страницы сохраняются при опросе и смене вкладки/запуска.
Ошибка загрузки сохраняет курсор; повтор продолжает с него.

Старые журналы открываются с добавлением таблиц. `metadata.usage` сохраняются; записи
каждого ответа/разбивка кэша не синтезируются. Структурные выходы родителей не считаются снова.

`task.usage` суммирует отдельные связанные запуски задачи. Нельзя одновременно складывать
строки отчётов, архивные попытки и накопительные метаданные. Повторно использованные
выходы не добавляют вызов модели и не считаются отсутствующими отчётами агента.
Оценка SDK не счёт подписки; неизвестная стоимость не ноль. Браузер переключает
«Этот запуск» / «Вся задача»; исходный сбой виден рядом с продолжением. Смена задачи
сбрасывает её прошлые суммы; выбор связанного запуска сохраняет режим всей задачи.

`tests/pi-worker.test.ts`, `tests/usage-pages.test.ts`, `tests/task-usage.test.ts` покрывают
настоящую сессию SDK с подставным транспортом, отчёт во время следующего хода, ошибку
схемы вывода, отмену; сохранность журнала, повторную/конфликтующую доставку, устаревшего
владельца, откат при отказе события; схему CLI/MCP и страницы HTTP браузера.
Эти проверки не расходуют подписку.

Парсер `usage` принимает обычные объекты и объекты с нулевым прототипом, читая
распознаваемые поля только как собственные перечислимые свойства с данными.
Унаследованные распознаваемые поля и свойства-доступоры отвергаются без вызова
функций чтения/записи свойства; дополнительные поля SDK не мешают разбору. Эта гарантия относится к `parseUsage`.
Отклонённый `recordUsage` не создаёт отчёт, агрегат или событие. Неизвестное значение
остаётся отличным от известного нуля. Регрессии: `usage-boundary`, `run-store`.

`usage-contract` отдельно защищает исключение всех структурных контейнеров из
повторного учёта и независимость признаков неполноты отдельных полей всей задачи:
например, неполная стоимость не делает неполными известные поля кэширования.
