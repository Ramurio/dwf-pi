# Создание графов, примеры и пресеты

[Индекс](README.md) · [Контракт графа](graph-contract.md) · [План и запуск](execution-plan.md)

Оглавление: [операции](#операции) · [версия](#атомарность-и-revision) ·
[совет ревьюеров](#council) · [пресеты](#presets) · [подготовка материалов](#read-boundaries).

[`src/authoring.ts`](../src/authoring.ts) даёт общий внутрипроцессный API для CLI
и инструментов MCP через `WorkflowService`. Агент выбирает блоки, поля и связи,
а не пишет циклы планировщика или исполняемый код оркестрации.

```ts
createDraft({ id: 'research-trio', name: 'Three independent researchers and a synthesizer' })
// revision: 1, entryGraph: 'main' уже создан; addGraph только для researcher-1/2/3

applyPatch(draft, {
  expectedRevision: 1,
  operations: [
    { op: 'addGraph', graphId: 'researcher-1' },
    { op: 'addNode', graphId: 'researcher-1', node: {
      id: 'investigate', kind: 'agent', role: 'researcher',
      task: { op: 'ref', path: ['input', 'assignment'] },
      input: { op: 'ref', path: ['input'] },
      config: {
        session: 'fresh', permission: 'read-only',
        tools: ['read', 'grep', 'find', 'ls'], skills: []
        // model.provider, model.id и thinking — из текущего catalog.models
      }
    } },
    { op: 'addNode', graphId: 'main', node: {
      id: 'research', kind: 'parallel', failurePolicy: 'collect',
      children: [
        { id: 'r1', graphId: 'researcher-1', input: { op: 'object', fields: {
          question: { op: 'ref', path: ['input', 'question'] },
          criteria: { op: 'ref', path: ['input', 'criteria'] },
          sources: { op: 'ref', path: ['input', 'sources'] },
          assignment: { op: 'ref', path: ['input', 'r1', 'assignment'] }
        } } }
        // r2, r3, synthesizer, finish accepted/inconclusive — в полном источнике
      ]
    } }
  ]
})
```

Это короткий фрагмент API данных, не полный рабочий цикл и не готовый к компиляции
граф согласования: нет контракта обратной связи, `artifactRevision` и корневого `finish`.
Исполняемый источник — JSON-запросы [research-trio](../skills/dynamic-workflows/recipes/research-trio/)
в установленном skill (create.json, patch.json, input.json и README.md). Не развивайте
здесь отдельный процесс реализации/ревью.

Перед запуском проверьте эффективные возможности `catalog.models` и при необходимости
задайте `config.requirements`. Снимки `config.skills` включают файлы выбранного skill,
в том числе вложенные исследовательские ресурсы, если они лежат в его каталоге.
Внешние исследования/проверки передавайте во вход и доказательства, не подразумевая,
что исполнитель сам их собрал. Большую работу делите на реализацию/проверку/ревью;
маленький граф можно оставить простым. `reuse` нужен только продолжению с уже завершённым выходом.

## Операции

Все поля строго проверяются; неизвестные поля/операции отвергаются.

| `op` | Дополнительные поля | Поведение |
| --- | --- | --- |
| `addGraph` | `graphId` | Добавляет пустой граф с входом `start`; существующий ID — ошибка |
| `removeGraph` | `graphId` | Удаляет существующий граф; `entryGraph` удалять нельзя |
| `addNode` | `graphId`, `node` | Добавляет новый ID; первый узел автоматически становится входом |
| `replaceNode` | `graphId`, `node` | Полностью заменяет существующий узел с тем же ID, без слияния `config` |
| `removeNode` | `graphId`, `nodeId` | Удаляет узел и все связанные управляющие рёбра |
| `setEntry` | `graphId`, `nodeId` | Назначает существующий узел входом |
| `connect` | `graphId`, `edge` | Добавляет ребро в конец массива; оба конца уже должны существовать |
| `disconnect` | `graphId`, `edgeIndex` | Удаляет ребро по текущему индексу; отсутствующий индекс — ошибка |

Операции пакета выполняются последовательно на копии. Можно добавить граф, затем узлы
и рёбра одним пакетом. Индексы рёбер после удаления сдвигаются; следующая операция
использует изменённый порядок. `removeNode` не подменяет вход автоматически: его удаление
отражается в проверке, пока автор явно не вызовет `setEntry`. Если удалены все узлы,
следующий `addNode` снова установит вход. Ссылки данных на удалённый узел и ссылки на
удалённый дочерний граф сохраняются и становятся ошибками проверки: данные не
переназначаются на другой узел молча.

<a id="атомарность-и-revision"></a>
## Атомарность и версия

`applyPatch` требует точного `expectedRevision`; несовпадение вызывает `RevisionConflictError`
с ожидаемым/фактическим значениями. Успех увеличивает `revision` один раз независимо
от числа операций. Пустой пакет отвергается. При ошибке все предыдущие операции
пакета отбрасываются; исходный черновик не изменён. Успешные `workflow`/`validation`
рекурсивно заморожены, входные узлы/рёбра скопированы.

Это атомарность чистой функции. При одновременных вызовах из разных процессов
хранилище должно сравнивать и заменять текущую `revision` в своей транзакции;
проверка внутри функции сама по себе не является блокировкой хранилища.
Изменение исполняемого неизменяемого снимка не входит в API редактирования.

На JSON-границе массив должен содержать все собственные индексы от `0` до
`length - 1`: лишнее свойство не компенсирует пропущенный элемент. Неплотный массив
отклоняется ранним `AuthoringError`, не меняя черновик и его версию.
Та же граница действует для JSON в схеме вывода. Регрессия: `json-array-boundary`.

## Незавершённый черновик и готовность к компиляции

`createDraft` намеренно возвращает пока невалидный для исполнения граф. Структура
каждого узла/ребра/`config`/`Expr` обязана быть корректной уже при изменении, включая
вход только из JSON, известные роли/инструменты и согласованные итоговые разрешения.
Можно ссылаться на будущие дочерние графы и ещё не завершённые выходы узлов;
отсутствие `end`, недостижимые узлы, двойной запасной переход и другие смысловые ошибки
возвращаются в `validation`, не откатывая корректную операцию над данными.

Для запуска сервис требует полноценной успешной проверки/компиляции. Непустой список
`issues` не превращается в предупреждение во время исполнения. Неизвестная операция `Expr`,
неверный корень `ref`, геттер, функция, `NaN`, цикл объектов или неверный `config` отвергают
сам запрос изменения.

Экспортируются `CreateDraftInput`, `DraftPatch` (псевдоним `PatchRequest`),
`AuthoringOperation`, `PatchResult` и соответствующие схемы `TypeBox`. `NodeSchema` и
`EdgeSchema` дополнительно экспортированы из контракта графа; семантика исполнения не меняется.

Проверки: `node --import tsx --test tests/authoring.test.ts`, `npm run typecheck`.
Тесты собирают цикл ревью из операций, проверяют готовность незавершённого черновика
к компиляции, устаревшую `revision`, откат пакета, remove/replace/`disconnect`, неизвестные
цели, защиту `entryGraph` и строгую границу JSON.

<a id="council"></a>
## Совет четырёх независимых ревьюеров

Каталог `examples/` содержит полный небольшой пример одного раунда ревью:
`examples/council.create.json` создаёт review-council; `examples/council.patch.json`
добавляет блоки/связи одним запросом с проверкой версии; `examples/council.input.json`
задаёт политику, артефакт/критерии и доказательства. Это запросы/данные, не код планировщика.
Не усложняйте пример продолжением/`reuse`/требованиями возможностей: для новой версии
реальной задачи используйте `run.continuation.inspect` → `run.continue`.
Переносимый research-trio, напротив, лежит [в skill](../skills/dynamic-workflows/recipes/research-trio/README.md),
а не в examples/src.

Сначала проверяется политика. При допустимой политике четыре параллельных вызова
общего графа `reviewer` (`correctness`, `verification`, `maintainability`, `requirements`)
переходят к `facts` → `verdict` → `result`; недопустимая сразу ведёт в invalid_policy,
без вызовов модели. У вызовов разные области и новые сессии, одинаковые `artifactRevision`,
критерии приёмки и их версия. До своего ответа ревьюер не видит голоса других.

Перспективы: корректность/краевые случаи; доказательства проверок; поддерживаемость/
интеграция; требования/границы задачи/совместимость. Используются настройки каталога
только для чтения, поэтому отдельных worktrees нет. Ревьюер проверок изучает реальные
отчёты инструментами чтения и не притворяется, что запускал команды. Передайте отчёты
или добавьте предшествующий `check`, если проверки нужно выполнить.

### Создать и запустить совет

После установки команды выполните из копии репозитория:

```sh
dynamicwf workflow.create < examples/council.create.json
dynamicwf workflow.patch < examples/council.patch.json

dynamicwf workflow.validate <<'JSON'
{"id":"review-council"}
JSON
```

Перед реальным ревью измените council.input.json: подставьте реальные пути/доказательства,
`artifactRevision` **проверяемого дерева**, а не просто текущий коммит. Для незафиксированной
работы сохраните идентичность дерева/разницы с этими правками. При изменении критериев
меняйте `acceptanceCriteriaRevision`. Идентификатор сам не замораживает файлы: держите
артефакт неизменным либо проверяйте неизменяемую копию/снимок.

`catalog.describe` и подготовка показывают настройки по умолчанию и итоговую конфигурацию.
При необходимости замените `reviewer.review` через `workflow.patch`, сохранив все исходные
поля и добавив нужный `config`. Общий узел применяется к четырём вызовам; для разных
моделей/уровней рассуждений создайте разные графы ревьюеров и направьте ветки в них.
Конфигурация фиксируется до старта.

После **каждой** команды проверяйте ok; у `patch` ещё `result.validation.valid`, у `validate` —
`result.valid`. Во всех командах используйте один --store, если журнал не стандартный.
Запускайте по просмотренному `preparedId`, не сокращённой формой с ID черновика и не
переопределяя `cwd`/`model`.

```sh
mkdir -p scratch/council
node -e 'const fs=require("node:fs"); process.stdout.write(JSON.stringify({id:"review-council",cwd:process.cwd()}));' | dynamicwf workflow.prepare > scratch/council/prepare-response.json
node -e 'const e=JSON.parse(require("node:fs").readFileSync("scratch/council/prepare-response.json","utf8")); if(!e.ok) throw new Error(e.error.message); process.stdout.write(e.result.preparedId+"\n");'
```

Изучите `result.plan` в сохранённом ответе, заранее выберите устойчивый `idempotencyKey`
и сохраните запрос только с `preparedId`/`input`/ключом:

```sh
node -e 'const fs=require("node:fs"); const prep=JSON.parse(fs.readFileSync("scratch/council/prepare-response.json","utf8")); if(!prep.ok) throw new Error(prep.error.message); const request={preparedId:prep.result.preparedId,idempotencyKey:"review-council-attempt-1",input:JSON.parse(fs.readFileSync("examples/council.input.json","utf8"))}; fs.writeFileSync("scratch/council/start-request.json", JSON.stringify(request));'
dynamicwf run.start < scratch/council/start-request.json > scratch/council/start-response.json
node -e 'const fs=require("node:fs"); const start=JSON.parse(fs.readFileSync("scratch/council/start-response.json","utf8")); if(!start.ok) throw new Error(start.error.message); const id=start.result.id; process.stdout.write(id+"\n"); process.stdout.write("dynamicwf watch --run "+JSON.stringify(id)+"\n");'
```

Немедленно выдайте настоящий `result.id` и команду watch с корректным экранированием,
до ожидания завершения (добавьте --store при его использовании). Потерянный ответ
повторяйте неизменным start-request.json; новое намеренное выполнение требует нового
ключа. `run.status`/`inspect` показывают результат: `succeeded` означает завершённый расчёт,
а `taskOutcome` и `output.accepted`/`decision` — принят ли артефакт. `request_changes`/
`inconclusive`/invalid_policy возможны при техническом успехе. Пресет автоматически не сохраняется.

### Политика и детерминированный итог

| Политика | Условие принятия |
| --- | --- |
| `unanimous` | Четыре `approve` |
| `three-of-four` | Не меньше трёх `approve` |

Отсутствующая/неподдерживаемая политика возвращает `{accepted:false,decision:"invalid_policy",...}`
до вызовов модели. `inconclusive` не даёт `approve`. `three-of-four` может перевесить один
`request_changes`/`inconclusive`, но сохраняет меньшинство и замечания. Если любой не-`approve`
должен блокировать приёмку, выберите `unanimous`. Скрытого вето/арбитражной модели нет.

`facts` использует `all`/`any`/`eq`; `three-of-four` — логическое «или» четырёх возможных троек
одновременного согласия. `verdict` через ленивый `select` выбирает `approve` при достижении
порога, иначе `request_changes` при любом таком голосе, иначе `inconclusive`. Это узлы
выражений, не подсчёт голосов моделью.

**Каждый** голос должен совпасть с обеими входными версиями. Хотя бы одно несовпадение
даёт `inconclusive`, `accepted`:`false`, `revisionConsistent`:`false` независимо от количества
`approve`. Исполнитель проверяет индивидуальные привязки, граф — сборку общего результата.
Отсутствующие обязательные поля дают ошибку вычисления, не выдуманное одобрение.
Результат сохраняет все четыре исходных голоса, сводки и замечания под ключами
перспектив, политику, ожидаемые версии, итоговое решение и признак согласованности.
Несогласие не переписывается в `approve`.

Пример не добавляет лимитов итераций/времени/токенов или человеческих согласований.
Для цикла реализации/ревью включите совет в больший граф, направьте `request_changes`
к производителю с фактическими замечаниями. `inconclusive` требует конкретных недостающих
доказательств, арбитража либо паузы управляющим приложением, а не согласия на словах.
`preset.save` принятого запуска уместен только явно; каждый повтор совета требует нового
валидного входа артефакта.

`tests/council.test.ts` загружает **эти** JSON через `WorkflowService`, проверяет/готовит
и исполняет сгенерированный граф `Effect`. Подставные голоса покрывают 81 комбинацию
трёх вердиктов четырёх ревьюеров при двух политиках (162 случая), отказ неверной политике
до допуска, несовпадение версии каждой позиции, сохранение замечаний и барьер четырёх
параллельных областей. Это проверка оркестрации/политики, не качества реальных ревью моделей.

<a id="presets"></a>
## Пресеты принятых графов

Для сохранения требуются `status:succeeded` и `taskOutcome.decision:accepted`.
Технически завершённый `rejected`/`inconclusive`/`unclassified` запуск не считается проверенным
пресетом. Старый `end` с `accepted`:`true` совместим. [Результаты и ожидания](outcomes-and-waits.md).

Пресет сохраняет **план исполнения успешного запуска**: граф, сгенерированный исходник,
модель, уровень рассуждений, полную системную инструкцию, инструменты, разрешения,
политику сессии, схему вывода и байты подключённых `skills`. Он не сохраняет вход/выход
запуска, расход, сессии pi, процессные токены или хранилище авторизации. Текст задания
и явно добавленные `skills` остаются частью шаблона: выбирайте область хранения с учётом содержания.

CLI и MCP используют одни операции:

```json
{"id":"run-UUID","name":"review-loop","scope":"project"}
```

Передайте это в `preset.save`. ID здесь — успешный **запуск**, не черновик графа.
`scope` бывает `project` (по умолчанию) и `global`. Неуспешный или работающий запуск нельзя
объявить проверенным шаблоном.

- Проект: `.dynamicwf/presets/<name>/<planHash>.json` в ближайшем корне Git, либо
  в указанном `cwd`, если корня Git нет. JSON можно хранить в Git.
- Глобально: `presets/` рядом с выбранной базой SQLite, по умолчанию `~/.dynamicwf/presets/`.

`preset.list` показывает обе области. Одноимённый проектный пресет имеет приоритет;
глобальная запись получает `shadowed`:`true`. Можно выбрать `scope` явно. `cwd` определяет
проект, а для запуска — также рабочую директорию.

```json
{"name":"review-loop"}
```

`preset.inspect` возвращает полный зафиксированный план. `preset.run` с теми же полями
плюс `input` создаёт **новый запуск**, ID и сессии. Исходный граф/план и старые записи
не меняются. Если модель больше недоступна, исполнитель завершится явной ошибкой,
а не подставит другую.

```json
{"name":"review-loop","scope":"global","input":{"task":"Следующая задача"},"cwd":"/absolute/project"}
```

Версия пресета — SHA-256 плана. `revision` выбирает конкретную сохранённую версию;
без него используется последняя по времени первого сохранения. Повторное сохранение
одинакового плана идемпотентно. Правка черновика не меняет сохранённый пресет.
Версии среды/компилятора проверяются при чтении; неподдерживаемые снимки не
интерпретируются по новым правилам.

Файлы публикуются атомарно созданием ссылки без перезаписи: незаконченная запись
никогда не становится читаемой версией. Проверяются хеш исходника/плана, зафиксированная
конфигурация, `skills` и пути. `tests/presets.test.ts` проверяет одновременное сохранение,
повреждение содержимого и реальный повторный запуск с изменённым входом.

Повторное сохранение того же плана сохраняет время первой записи. Версии
упорядочены по `savedAt`, а при равенстве — по `revision.localeCompare`; последняя
запись определяет актуальную версию. `presets` проверяет этот порядок, полные записи
и одновременные сохранения без ожиданий по таймеру.

Для новых задач есть переносимые [рецепты реализации с ревью](../skills/dynamic-workflows/recipes/implementation-review/README.md):
S — последовательная схема, P — параллельное планирование и предварительное ревью,
C — два финальных ревьюера с обязательным одобрением обоих. Рецепт создаёт новый
граф под задачу; сохранённый проверенный пресет повторяет уже зафиксированный план.

Параметры рецепта: `task`, `acceptanceCriteria`, `projectPolicy`, `contextFiles`,
`checkCommand` и `checkArgs`; `id` и `name` задают новый граф. Применимые инструкции
AGENTS передают явно в `projectPolicy`. Целевую рабочую копию задают через `cwd`
при подготовке; отдельное рабочее дерево создаётся от текущего чистого `HEAD`.
Параметров `repo` и `base` во входе рецепта нет. Результат возвращается как
отдельное рабочее дерево с коммитом;
автоматического слияния нет.

Три схемы проверены реальными принятыми запусками; в локальной коллекции они
сохранены как `astra-implementation-review`, `astra-preflight-implementation-review`
и `astra-implementation-council`. Эти записи фиксируют в том числе команду проверки
и не становятся доступными в другой установке от одного копирования skill.
Изменение `input.checkCommand` или `input.checkArgs` не заменяет сохранённую команду:
для новой команды создайте рецепт через `instantiate.mjs` и подготовьте новый план.
Принятый запуск подтверждает свою задачу и версию, а не качество любых будущих задач.

<a id="read-boundaries"></a>
## Подготовка материалов для исполнителей только с чтением

### Проверенная граница

`tests/read-boundary.test.ts` использует настоящий локально установленный
`@earendil-works/pi-coding-agent` 0.85.1 `read`, без модели и сети.
Текстовый ответ ограничен 2000 строками или 50 KiB (51200 байт). Если первая выбранная
строка превышает байтовую границу, SDK возвращает `firstLineExceedsLimit`, пустое
`truncation.content` и ноль `outputBytes`: содержимое **недоступно**, не молча обрезано.
`offset`/`limit` считают строки, не байты. У однострочного JSON `offset`=2 уже за концом файла;
уменьшение `limit` не открывает часть первой строки.

SDK предлагает `Use bash`, но это диагностика, не разрешение. Проверка без модели
подтверждает список `read, submit_result` до и после предупреждения и отказ при вызове
отсутствующего `bash`. `write`/`edit` тоже не появляются. Не выдавайте их исследователю
только с чтением ради обхода границы.

### Что должен подготовить владелец входных данных

1. Сохраните оригинал и исходные наблюдения без потерь, отдельно от резюме/выводов.
   Не заменяйте их пересказом и не обрезайте значения.
2. Для JSON с короткими значениями подготовьте многострочную копию (например, отступ 2),
   сохранив типы/значения. Проверьте обратный разбор и равенство; оригинал храните отдельно,
   особенно если парсер может терять точность чисел или повторяющиеся ключи.
3. Читайте копию страницами по строкам, следуя `offset` в уведомлениях SDK. Тест собирает
   JSON больше 50 KiB из страниц по 100 строк, сверяя начало/конец, весь текст и значения.
4. Форматирование **не спасает одно огромное строковое значение**: строка остаётся
   больше 50 KiB. В тесте скобки читаются, значение — нет.
5. Для таких значений владелец заранее готовит отдельные части UTF-8 безопасного размера
   (например, до 16 KiB, без разрыва символа). Не добавляйте разделители/новые строки,
   меняющие текст. Приложите доступный многострочный манифест: источник и JSON-путь значения,
   кодировка, способ извлечения (исходные байты или декодированное значение), порядок частей,
   имена, длины в байтах, SHA-256 каждой части и объединённого текста. Соединение байтов
   в указанном порядке должно воспроизвести выбранный текст с общей контрольной суммой.
   Оригинал JSON и исходные наблюдения остаются отдельно. Это подготовка владельца,
   не новая возможность исполнителя.
6. Если частей нет, явно укажите: «Содержимое недоступно через `read`: файл …, строка …,
   `firstLineExceedsLimit`; выводы по нему не сделаны». Предупреждение не является прочитанным материалом.

### Ограничения

`read-only` не разрешает инструменты изменения; сжатие контекста отключено. Это инструкция
подготовки материалов, не новый инструмент чтения диапазона байтов и не доказательство
влияния длинного контекста на качество модели.
