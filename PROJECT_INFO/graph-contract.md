# Контракт графа и компиляция

Статический граф задаёт порядок работы, циклы и вложенные графы. Среда исполнения
выбирает переходы и создаёт динамические экземпляры `map`, не меняя схему. Ни один узел
не содержит JavaScript, TypeScript или `eval`. Реализация контракта:
[`src/graph.ts`](../src/graph.ts); роли: [`src/catalog.ts`](../src/catalog.ts).

## Внешняя форма

```ts
WorkflowDefinition = {
  schemaVersion: 1;
  id: string;
  name: string;
  revision: number; // положительное целое
  entryGraph: string;
  graphs: Record<string, Graph>;
}
Graph = { entry: string; nodes: Node[]; edges: Edge[] }
Edge = { from: string; to: string; when?: Expr }
```

Идентификаторы определения процесса, графа, узла и ребёнка `parallel` имеют форму
`^[A-Za-z][A-Za-z0-9_-]*$`. ID узла локален графу, ID ребёнка — узлу `parallel`.
Один дочерний граф можно использовать в нескольких местах. `revision` меняется при
сохранении изменённой схемы; исполнение закрепляет конкретный снимок до запуска.
`parseWorkflow` проверяет, клонирует и рекурсивно замораживает результат, поэтому
правки исходного черновика не меняют принятую схему. Прямой `validateWorkflow`
возвращает `{valid, issues}` и не меняет объект.

Узлы имеют обязательные `id`, `kind` и следующие поля:

| `kind` | Поля | Значение результата |
| --- | --- | --- |
| `agent` | `role`, `task: Expr`, `input?: Expr`, `config?: AgentConfig`, `retryPolicy?: RetryPolicy` | Проверенный JSON-объект исполнителя pi по итоговой `outputSchema` |
| `transform` | `value: Expr` | Вычисленное значение |
| `branch` | `input?: Expr` | Вычисленный вход, либо текущий вход графа |
| `map` | `graphId`, `items: Expr`, `concurrency?: positive integer`, `failurePolicy?: fail-fast/collect` | Массив результатов дочернего графа в порядке исходных элементов |
| `parallel` | `children: {id, graphId, input: Expr}[]`, `concurrency?: positive integer`, `failurePolicy?: fail-fast/collect` | Объект с результатами по ID детей |
| `subworkflow` | `graphId`, `input: Expr` | Результат дочернего графа |
| `worktree` | `graphId`, `input: Expr`, `base?: string` | `{result,workspace:{path,branch,base,head}}`; дочерний граф в отдельной Git-ветке |
| `integrate` | `sources: Expr` | Явное слияние завершённых результатов `worktree` этого запуска; фактический `head` и слитые коммиты |
| `check` | `command: string`, `args: string[]`, `cwd?: string`, `retryPolicy?: RetryPolicy` | `{exitCode,stdout,stderr}`; обычный ненулевой код выхода — данные, не исключение исполнения |
| `end` | `value: Expr` | Результат текущего графа |
| `finish` | `decision: accepted/rejected/inconclusive`, `reason: Expr`, `evidence: Expr`, `value: Expr` | Результат графа и отдельное решение о его приёмке |
| `await` | `reason: Expr`, `input: Expr`, `responseSchema: object` | Сохраняемый ответ по строгой схеме |
| `reuse` | `bindingId`, `outputSchema: object` | Точный снимок уже завершённого выхода; только через `run.continue`, без вызова модели |

Контракты завершения и ожидания, API и восстановление — в [исходах](outcomes-and-waits.md).
`finish`, как и `end`, терминален. `await` продолжает граф по обычным рёбрам после ответа;
схема проверяется до запуска.

`failurePolicy` по умолчанию `fail-fast`; при `collect` каждый результат дочернего графа
оборачивается в `succeeded`/`value` или `failed`/`failure`, без превращения ошибки в вердикт.
См. [сбор ветвей](outcomes-and-waits.md#collection). `RetryPolicy` относится к узлу `agent`/`check`,
не к `config`; без явной политики автоматический повтор выключен. Допустимые причины,
задержки и ограничения эффектов — в [политике повторов](retry-and-failures.md#retry).

`map.items` во время исполнения должен дать JSON-массив. Каждый элемент становится
`input` отдельного дочернего экземпляра. `subworkflow.input` и `parallel.children[].input`
тоже передают JSON напрямую. Родительские узлы не видны внутри ребёнка: нужный контекст
передаётся явным входом. Отсутствующий `concurrency` означает отсутствие заданного
пользователем ограничения, а не скрытый фиксированный предел.

`check.command` — имя исполняемого файла или путь, `args` — массив аргументов.
Среда исполнения не соединяет их в строку оболочки. Например
`{command:"node",args:["--version"]}`. Явный `bash` с -c остаётся запуском оболочки,
которую пользователь указал сам; ограничения доступа должен применять исполнитель.
NUL в аргументах и `cwd` запрещён.

## Переходы и завершение

После узла проверяются его условные рёбра **в порядке массива**. Выбирается первое
условие со значением `true`. Если ни одно не подошло, используется единственный безусловный
запасной переход независимо от позиции в массиве. Если подходящего ребра нет, нужна
ошибка маршрутизации, не неявный успех. Условия должны давать `boolean`, без автоматической
трактовки других значений как истинных/ложных в JavaScript.

Одно исходящее ребро — обычная последовательность. Несколько условных — выбор пути.
Разветвление задаётся `map`/`parallel`, не несколькими безусловными рёбрами. Возврат к ранее
посещённому узлу — цикл, разрешён без `maxIterations` по умолчанию. `end`/`finish` не имеет
исходящих рёбер. Рекурсивные ссылки на дочерний граф запрещены, включая взаимную рекурсию
через `map`/`parallel`/`subworkflow`.

Валидатор проверяет существование входов/ссылок, уникальность ID, достижимость всех
узлов из `entry`, структурный путь от каждого узла до `end`/`finish` и достижимость каждого
графа из `entryGraph`. Он **не вычисляет условия**: статический путь к `end` не доказывает
завершение конкретного запуска. Цикл «ревью → доработка» может продолжаться до `approve`;
остановка/пауза относятся к среде исполнения.

## AST выражений

```ts
{ op: 'literal', value: Json }
{ op: 'ref', path: string[] }
{ op: 'object', fields: Record<string, Expr> }
{ op: 'array', items: Expr[] }
{ op: 'get', value: Expr, path: string[] }
{ op: 'select', when: Expr, then: Expr, otherwise: Expr }
{ op: 'eq' | 'ne' | 'gt' | 'gte' | 'lt' | 'lte', left: Expr, right: Expr }
{ op: 'all' | 'any', items: Expr[] }
{ op: 'not' | 'exists', value: Expr }
```

Корни `ref`: `input` и `nodes`. `['nodes','review','decision']` читает поле `decision`
**последнего завершённого посещения** review в текущем экземпляре графа. Ссылка на
несуществующий ID узла отвергается. Ссылка на существующий, но ещё не завершённый узел
разрешена — например, для условной передачи обратной связи цикла через `exists`.
`select` вычисляет только выбранную ветвь; `when` обязан быть `boolean`. Это позволяет
передать исполнителю исходное задание в первом посещении, затем результат последнего
ревью: `select(exists(nodes.review), nodes.review, input)` в форме AST выше.
Поведение отсутствующих значений, ошибки сравнения и строгий `boolean` закрепляет
вычислитель; отсутствие нельзя молча заменять `null`. Путь — сегменты, поэтому точка
внутри имени JSON-поля не разделитель. Произвольный код, вызовы функций, доступ к
процессу/окружению и дополнительные поля AST запрещены.

## Роли и настройки исполнителя

Встроены `general`, `researcher`, `planner`, `implementer`, `reviewer`, `verifier`,
`synthesizer`, `arbiter`, `orchestrator`. Oracle не реализован. Незнакомая роль отвергается;
реестр расширений потребует отдельного контракта.

`AgentConfig` частично переопределяет настройки роли по умолчанию:

- `model?: {provider, id}` — без секретов и неподтверждённой модели по умолчанию.
- `thinking?: off | minimal | low | medium | high | xhigh | max` — уровень рассуждений.
- `systemPrompt?: string` — полная замена инструкции роли, если явно задан.
- `tools?: string[]` — замена списка; разрешён встроенный набор pi: `read`, `bash`, `edit`, `write`, `grep`, `find`, `ls`.
- `skills?: string[]` — явные ссылки на ресурсы `skills`; их наличие проверяется при подготовке.
- `session?: fresh | continue-node` — новая либо продолжаемая сессия узла.
- `permission?: read-only | workspace-write | unrestricted` — профиль разрешений.
- `outputSchema?: object` — JSON Schema результата с корневым типом `object`.
- `outputRepair?: {mode: disabled} | {mode: submit-only, maxRounds?: positive safe integer}` —
  [исправление формата](retry-and-failures.md#output-repair) в той же сессии, по умолчанию `disabled`.
- `requirements?: {inputModalities?: (text | image)[], toolResultModalities?: (text | image)[]}` —
  требования к эффективным возможностям; подготовка и исполнитель отвергают неизвестную
  или неподдерживаемую требуемую модальность. См. [план](execution-plan.md).

Ревьюер получает новую сессию, инструменты только для чтения, `thinking` high и строгую
`outputSchema` с `decision: approve | request_changes | inconclusive`, `summary`, `findings`
и обязательной `artifactRevision` проверенной версии результата. Необязательная
`acceptanceCriteriaRevision` связывает вывод с версией критериев. Версии нельзя выдумывать:
их передают во вход ревью. Результат отправляется через назначенный инструмент результата.
Замечание содержит `severity`/`message`, необязательно `file`/`line`/`evidence`/`suggestion`.
Политика совета строится поверх результатов, не вшита в каталог.
Реализатор (`implementer`) продолжает сессию узла и имеет `workspace-write`. Проверяющий
(`verifier`) получает `bash` и `workspace-write`, поскольку проверки могут писать временные
артефакты. Остальные роли по умолчанию получают инструменты чтения и новую сессию.
Все инструкции требуют подтверждать фактические действия и отделять внешние данные
от управляющих инструкций.

Конфигурация с итоговым `read-only` и `bash`/`edit`/`write` отвергается с учётом значений
по умолчанию. Исполнители работают отдельными процессами; профили разрешений задают
инструменты/инструкции, не изоляцию ОС или запрет выхода команд за пределы каталога.
Worktrees координируют параллельные записи и интеграцию. Совместимость модели/уровня
рассуждений проверяется по установленному каталогу pi до запуска. В графе нет скрытых
лимитов стоимости, времени, циклов или разветвления.

## Границы проверки

Интерфейс создания графов публикует `TypeBox`-схемы `WorkflowSchema`, `ExprSchema`,
`AgentConfigSchema`. Все структурные объекты закрыты для неизвестных полей. Литералы
и `outputSchema` содержат только JSON: отклоняются `undefined`, `NaN`/`Infinity`, `BigInt`,
функции, циклические объекты, разреженные массивы, геттеры и нестандартные прототипы.
Проверка графа компилирует итоговую `agent` `outputSchema` (включая роль/общее значение
по умолчанию), `await.responseSchema` и `reuse.outputSchema` тем же строгим валидатором,
что и подготовка. Неверный корневой тип, неподдерживаемые ключевые слова, диалекты и
внешние ссылки дают ошибки до запуска исполнителя. Доступность модели/уровня рассуждений,
файлов skill и рабочего каталога проверяется отдельно при подготовке плана.

Проверка графа также выявляет агентов с правом записи и `integrate` в общей
параллельной области без собственного `worktree` внутри ветви. Она использует
итоговое разрешение роли, а не имя роли или обещание писать в разные файлы.
Это общая проверка для `patch`, `validate`, компиляции и подготовки;
сохранённые планы проверяются по зафиксированным разрешениям.
Эффекты произвольных `check` автоматически не выводятся. Подробнее:
[параллельные записи](workspaces.md#writers).

Проверки: `node --import tsx --test tests/graph.test.ts` и `npm run typecheck`.
Тесты покрывают реальный цикл доработки, вложенное разветвление, отрицательные случаи
связности/рекурсии, строгие JSON/AST/`config`, неизменяемый снимок и схему ревьюера.
`tests/campaign-schema.test.ts` закрепляет раннюю компиляцию `outputSchema`.

Наборы `campaign-schema` и `execution-plan` используют общие неизменяемые данные
из `tests/helpers/schema-cases.ts` и сверяют статические диагностики валидатора
вывода, проверки графа и подготовки плана. При отказе подготовки проверяется полный
массив `issues`; невалидная схема отклоняется до чтения моделей.

## Компиляция в TypeScript + `Effect`

`compileWorkflow(unknown)` из `src/compiler.ts` вызывает `parseWorkflow`, получает
независимую замороженную копию определения и возвращает `{ source, hash, workflow, compilerVersion }`.
Невалидная схема отвергается до генерации. `hash` — SHA-256 UTF-8 исходника; ключи JSON
и порядок определения функций графов канонизированы, порядок массивов сохраняется.
В частности, порядок условных рёбер значим. Это хеш **исходника**, не зафиксированного
плана исполнения или окружения моделей.

Сгенерированный модуль импортирует `effect`, `dynamicwf-pi/expressions`, типы
`dynamicwf-pi/graph` и `dynamicwf-pi/runtime-contract`. Его публичная функция:

```ts
run(runtime: WorkflowRuntime, input: Json): Effect.Effect<Json, Error>
```

Она вызывает сгенерированную функцию входного графа. Для каждого графа компилятор
создаёт функцию с `Effect.gen`, локальными `nodes`/visits, счётчиком команд, while/switch.
Это сгенерированный управляющий код, не интерпретация JSON-графа средой исполнения.
Выражения остаются данными AST и выполняются ограниченным `evaluate`; выбор стрелки —
`chooseEdge`. Тексты задания/инструкций/команд/литералов и поля объектов сериализуются
как JSON, не становятся JavaScript. JSON.parse сохраняет собственный ключ __proto__ как данные.

### Исполнение блоков

- `agent` вычисляет `task`, требует строку и передаёт вычисленный `input` исполнителю.
  С v10 `runtime.stepOperation` получает ленивую подготовку входов и сохраняет их атомарно
  с допуском задачи; v1–v9 сохраняют вызов `runtime.agent` внутри обычного `step`. Без `input` использует копию входа текущего вызова графа; `null` можно задать литералом.
- `check` делегирует `command`/`args`/`cwd` в `runtime.check`; компилятор сам не запускает оболочку/подпроцесс.
- `transform` возвращает вычисленное `value`.
- `branch` возвращает вычисленный `input`, без привязки — копию входа текущего графа; затем выбирает ребро.
- `end` возвращает вычисленное `value` как результат вызова графа без следующей стрелки.
- `finish` вычисляет `reason`/`evidence`/`value`, сохраняет решение через `runtime.finish` и завершает вызов.
- `await` вычисляет `reason`/`input`, вызывает `runtime.wait`; после сохранённого ответа выбирает обычное ребро.
- `reuse` (v9) возвращает `runtime.reuse` без выражений и модели; требует квитанцию продолжения.
  Компиляторы v1–v8 отвергают этот вид узла.
- `subworkflow` вызывает конкретную сгенерированную функцию дочернего графа с её входом.
- `map` требует массив `items` и вызывает дочернюю функцию через `Effect.forEach`;
  результат — массив в порядке входа, независимо от завершения.
- `parallel` генерирует функции ветвей и `Effect.forEach`; результат — объект по ID детей,
  порядок включения соответствует `children`.
- `worktree` передаёт среде исполнения функцию дочернего графа; область и директорию
  определяет изолированное рабочее дерево Git.
- `integrate` вычисляет `sources` и передаёт явное слияние зафиксированных результатов Git в исполнение.

С v3 каждый нетерминальный блок выбирает следующее ребро через `runtime.route`:
решение сохраняется до допуска следующего узла. [Трасса](observation.md#routing-trace).
Исходник v1/v2 сохраняет прежний `chooseEdge`.

У `map`/`parallel` число `concurrency` передаётся в `Effect` явно. Без поля используется
`unbounded` согласно решению об отсутствии скрытого ограничения параллелизма; ограничения
ОС/провайдера остаются. У циклов нет встроенного `maxIterations`; выход задают рёбра,
остановку обеспечивает прерывание `Effect`/среда исполнения. Повторный визит заменяет
`nodes`[`nodeId`] последним завершённым результатом; остальные завершённые значения
сохраняются в пределах вызова графа. Соседние/дочерние вызовы имеют отдельные записи.

Каждый блок, включая `end`/`map`/`parallel`/`subworkflow`/`branch`/`transform`, исполняется через
`runtime.step(context, work)`. Внутри `work` — вычисление входа и дочерние вызовы.
`JournalRuntime` может не вызывать отложенное вычисление и вернуть сохранённый результат;
планировщик восстанавливает локальный порядок исполнения через контрольные точки.

### Идентичность активаций

`RuntimeContext` содержит `graphId`, `nodeId`, `scope: readonly string[]`, `visit`.
`visit` начинается с 0 отдельно для каждого узла в каждом вызове графа. Корневая область:
`["graph", entryGraph]`. Дочерняя область добавляет сегменты:

```text
node, parentNodeId, visit, parentVisit, map, itemIndex, graph, childGraphId
node, parentNodeId, visit, parentVisit, parallel, childId, graph, childGraphId
node, parentNodeId, visit, parentVisit, subworkflow, graph, childGraphId
node, parentNodeId, visit, parentVisit, worktree, graph, childGraphId
```

Журнал хранит кортеж JSON `[scope, graphId, nodeId, visit]`, не склеивает произвольные
сегменты разделителем. ID запуска добавляет внешняя среда: один скомпилированный граф
имеет одинаковую структуру областей в разных запусках. Нельзя разделять локальные
записи/счётчики между параллельными дочерними вызовами.

### Проверка и текущие границы

`tests/compiler.test.ts` проверяет диагностику TypeScript **сгенерированных** модулей
со строгими флагами, транспилирует установленным TypeScript, записывает временные .mjs,
импортирует и исполняет через `Effect` с подставной средой. Проверяются отказ ревью →
обратное ребро → `approve`, `map`+`parallel`+`subworkflow`, порядок результатов при разных
временах завершения, фактическое перекрытие ветвей, уникальность `scope`/`visit`, `step` для
всех структурных узлов, `branch`/`check`, неизменный вход по умолчанию, детерминированный
хеш, похожие на код литералы и ключи прототипов как данные, неверный граф и нестроковый `task`.

Компилятор остаётся чистым: настройки по умолчанию/модели определяет `prepareExecutionPlan`,
исполнение обеспечивает `JournalRuntime` в отдельном supervisor. Зафиксированный план
связывает исходник/хеш с версиями компилятора/среды исполнения, моделями и ресурсами.
`loadGeneratedModule` перенаправляет только импорты компилятора
на установленную среду и выполняет модуль из внешнего каталога запусков. Произвольные
данные графа не становятся импортами. Исполнители pi проверяют структурированный вывод,
возможности и завершение работы. Журнал не обещает однократность внешних эффектов:
неопределённое действие после аварии нельзя повторять автоматически. [Журнал](run-journal.md).

Поля `object.fields` вычисляются в лексикографическом порядке ключей, включая
числоподобные имена: прямой evaluator и скомпилированный граф имеют одинаковый
приоритет ошибок. Порядок элементов массивов и условных edges сохраняется.
Граница прямого TypeScript API принимает обычные плотные JSON-массивы, но не
наследников Array с изменённым прототипом. Знак `-0` не является отдельным
контрактом DSL: JSON-доставка и канонический исходник нормализуют его в `0`.

## Worktree tree constraint

Необязательный `expectedTreeFromResult: string[]` — путь относительно результата ребёнка;
`[]` выбирает корень. Значение: точная строка `git-tree:<полный lowercase SHA-1/SHA-256 OID>`
или явный `null` (без ограничения). Missing path, промежуточный null и неверный тип/формат
отвергаются. Без selector поведение совместимо со старыми графами. Поле сохраняется
в скомпилированном frozen плане; старые планы и пресеты автоматически guard не получают.
