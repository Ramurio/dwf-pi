# Ошибки, HTTP-наблюдения, повторы и исправление вывода

[Индекс](README.md) · [Журнал](run-journal.md) · [Явное восстановление](reconciliation.md)

Оглавление: [типизированные ошибки](#failures) · [HTTP](#provider) ·
[автоматический повтор](#retry) · [исправление формата](#output-repair) · [проверки](#tests).

Механизмы не взаимозаменяемы: наблюдение описывает причину, политика повторов допускает
новую безопасную попытку, исправление вывода меняет формат в уже работающей сессии,
явное восстановление разрешает неопределённые эффекты. `collect` лишь сохраняет результаты ветвей.

<a id="failures"></a>
## Типизированные ошибки и внешние эффекты

Закрытая запись `{version:1,code,phase,effects,message}` проходит через обмен с pi/`check`,
`Effect`, журнал, CLI/MCP и интерфейс. Допустимы проверенные необязательные `providerResponse`
и `diagnostic`. Старые строки ошибок остаются технической диагностикой, не политикой повторов.

`code`: `configuration`, `resource`, `provider`, `output`, `process`, `protocol`,
`cancelled`, `interrupted`, `expression`, `uncertain-effect`, `unknown`.
`phase`: `setup`, `execution`, `output`, `routing`, `recovery`, `cleanup`, `unknown`.
Фаза относится к причине, не прогрессу всего графа: подготовка исполнителя может
завершиться ошибкой уже после записей предыдущих узлов.

| `effects` | Значение для наблюдаемой операции |
| --- | --- |
| `not-started` | Задание не допущено: исполняемый файл отсутствует, подготовка/настройки/ресурсы отвергнуты, отмена произошла до допуска процесса |
| `read-only` | Проверенный исполнитель pi имел только инструменты чтения либо упало чистое выражение; это не изоляция ОС |
| `unknown` | Действия могли произойти или исход не установлен; неправильный JSON исполнителя не отменяет его запись |

Разворачивание приватных ресурсов/сессии, доступ к аккаунту и стоимость SDK — не
эффекты задания, описываемые этим полем. `not-started` не обещает откат всех локальных
метаданных. Исчезновение процесса не доказывает отсутствие действий. Структурные родители
и сводка запуска консервативно сохраняют `unknown`: отказ одного узла только для чтения
ничего не доказывает о соседях/предыдущих узлах. Конкретные факты читайте у активации/попытки.

Исполнитель создаёт типизированный `ExecutionFailure` только в известных точках:

- Ошибка отправки результата или проверки его схемы получает код `output`.
- Несоответствие модели, инструментов, уровня `thinking` или сессии — код `configuration`.
- Отсутствующий или небезопасный ресурс зафиксированного плана — код `resource`.
- Неподтверждённое завершение работы — `code: process`, `phase: cleanup`, `effects: unknown`.

Ошибка ответа ассистента в SDK относится к `provider`; неизвестные исключения SDK
остаются `unknown`. Из текста ошибки или совпадения префикса нельзя выводить статус HTTP,
отказ авторизации, временный характер сбоя, ограничение частоты запросов или допустимость
повтора. Это предотвращает утечку произвольного хвоста сообщения под видом доверенной диагностики.

Обычный выход `check` с кодом 1/7 возвращает `{exitCode,stdout,stderr}` как данные графа;
отрицательный вердикт ревьюера — тоже данные. Отсутствующий исполняемый файл до допуска
отличается от потери процесса после допуска, которая не может утверждать `not-started`.

Декодер IPC проверяет точные поля/версию/перечисления и запрещённые свойства-геттеры.
Старая нетипизированная ошибка остаётся `unknown`. Неверный поток сообщений даёт ошибку
протокола без сырого stdout. Первая ошибка прекращает обработку сообщений/событий;
последующие не заменяют причину. Успешный поток содержит ровно один результат-объект
и ничего после него, кроме пустых строк. Схему содержимого проверяет исполнитель.

### Сохранение и интерфейсы

`metadata.failure` записывается атомарно с ошибкой/прерыванием/событием. Новая попытка
архивирует старую запись и очищает текущую ошибку, сохраняя контрольные точки каталога/ожиданий.
Составные ошибки `agent`/`check` сохраняют `metadata.failureCauses` и поле события `causes`,
даже если повтор отказан: каждая причина участвует в выборе, нельзя скрыть запрещённый
второй статус за первым. Новая попытка очищает причины после архива; старые записи
без списка не получают выдуманных причин.

`RunRecord.failure` хранится отдельно для `failed`/`interrupted`; успех его очищает.
Сводка, инспекция и события сохраняют типизированную причину; ответ об ошибке CLI/MCP
включает её только если приложение действительно подняло типизированный отказ.
Старые строки ошибок не классифицируются задним числом. Это добавочные поля журнала/IPC,
без изменения исходника/хеша прежних планов. Сводка браузера объясняет остановку,
детали узла/попытки — эффекты и причины. Watch показывает `code`/`phase`/`message` вместо
стека вызовов в строке состояния.

<a id="provider"></a>
## HTTP-наблюдения провайдера

```json
{"version":1,"code":"provider","phase":"execution","effects":"read-only",
 "message":"Pi assistant turn failed or was aborted",
 "providerResponse":{"status":429,"retryAfterMs":12000}}
```

`status` — наблюдённый HTTP 100–599, не число из текста ошибки. Retry-After принимается
как целое число секунд задержки или корректная IMF-fixdate: неверные/небезопасные значения
отсутствуют, прошедшая дата даёт 0, абсолютная дата считается по локальным часам исполнителя.
Тело, cookies, URL, авторизация и произвольные заголовки в запись не входят.

У каждого запроса ассистента отдельное наблюдение. Следующая сетевая ошибка не наследует
предыдущий статус, в том числе между ходами с инструментами и раундами исправления.
Факты прикрепляются только к неудачному ходу ассистента. HTTP 200 с оборванным потоком
остаётся 200, не успехом работы и не вымышленной серверной ошибкой. Прерывание графа
сохраняет семантику отмены.

SDK `onResponse` на некоторых путях OpenAI вызывается лишь после успешного допуска,
поэтому исполнитель дополнительно оборачивает fetch **отдельно для каждого запроса**
к `openai-completions`, `openai-responses`, `openai-codex-responses`, `xai-responses`:
наблюдает отказ до очистки диагностики и возвращает исходный Response без изменения.
Остальные API используют функцию обратного вызова SDK и сообщают лишь доступные факты.
Глобальной подмены fetch нет.

Повторы сессии и HTTP отключены (`maxRetries:0` на каждом запросе). Codex идёт по SSE:
цикл продолжения/запасного транспорта WebSocket закреплённого SDK может повторять
независимо от `maxRetries`. Отключения одних повторов сессии недостаточно. Выбор модели,
уровня рассуждений и допуск работы графа при этом не меняются.

Обновление авторизации/каталога до вызова модели и транспорты без доступа к ответу могут
завершиться ошибкой без HTTP-фактов. Отсутствие означает неизвестность, не ноль и не
«временную ошибку». Коды из тела/произвольные сообщения не используются для классификации.
Диагностика запроса различает `not-dispatched`, `fetch-attempted`, `http-observed`, `unknown`;
настроенный уровень рассуждений не заменяет наблюдаемый `sentReasoning`.

Необязательное поле проверяется на границах IPC/ошибки/журнала, включая закрытые вложенные
поля и запрет геттеров. Старые записи версии 1 без него валидны. Контрольные точки,
результаты `collect`, решения о повторах, архивы, сводки, сервис/MCP/браузер/watch сохраняют
те же факты. Учёт независим: HTTP-ошибка не превращает неполный расход в полный или нулевой.
В v7+ политика может выбрать статусы/Retry-After; само наблюдение повтор не разрешает.
Граф может явно использовать факты ошибки `collect` в последующих решениях.

<a id="retry"></a>
## Явный автоматический повтор

Политика принадлежит узлу `agent`/`check`, **вне** конфигурации агента:

```json
{"codes":["process","provider"],"delayMs":5000,"maxAttempts":3,
 "provider":{"statuses":[429,503],"retryAfter":"honor"}}
```

Без политики автоматический повтор выключен. `codes` — непустой уникальный список
допустимых семейств ошибок; `delayMs` — обязательное неотрицательное безопасное целое.
Необязательный `maxAttempts` — положительное безопасное целое, включает первую попытку;
без него число попыток не ограничено. Политика зафиксирована в плане, не меняет топологию
и не повторяет всю ветку.

**Каждая** причина должна соответствовать `codes` и подтверждённым `effects` `not-started`/`read-only`.
Отмена, прерывание, `uncertain-effect`, дефекты `Effect` и ошибки завершения/очистки не входят
в цикл. Ненулевой код `check` и вердикт ревьюера не являются причинами повтора.
Исполнитель с правом записи может подходить до допуска задания, но после допуска
неопределённые эффекты запрещают повтор, даже при неправильном финальном JSON.
Для формата существует исправление в той же сессии после завершения работы, не повтор
записывающего задания. Вызовы модели только для чтения всё равно тратят токены.

Без `provider.statuses` код `provider` выбирает всё сообщённое семейство, даже без HTTP.
Непустой уникальный список целых 100–599 фильтрует по **наблюдаемому** статусу;
отсутствующий статус фильтр не проходит. HTTP 200 может сопровождать оборванный поток.
Фильтр не влияет на другие коды. Параметры `provider` требуют `provider` в `codes`.

`provider.retryAfter:"honor"` берёт максимум `delayMs` и всех валидных серверных задержек
причин; отсутствующий/неверный заголовок оставляет настроенную задержку. Значение `ignore`
или отсутствие опции также оставляет её. Скрытого ограничения серверной задержки нет;
заголовок не уменьшает минимум и не разрешает неопределённые записи. Составная ошибка
целиком должна пройти политику. Неограниченный повтор постоянной ошибки продолжается
до паузы/отмены.

### Решение и допуск

Контрольная точка ошибки, неизменяемое решение, прогресс и событие фиксируются вместе.
Решение содержит неудачную/следующую попытку, причину (и все составные причины), время
планирования и выбранную задержку. Допуск в транзакции сверяет попытку, точное решение,
прогресс, ошибки и зафиксированную политику, архивирует неудачную контрольную точку
с отметкой допуска и начинает новую попытку. Использованное решение не разрешает
повтор после аварии во время исполнения.

`metadata.retry.status`: `scheduled`/`admitted`/`abandoned`. Состояние `scheduled` ещё не
означает исполнение. При окончательном завершении запуска незавершённые решения
переводятся в `abandoned`, история сохраняется. Новое ручное решение восстановления
`accept`/`retry` атомарно переводит запланированный повтор **только этой активации** в
`abandoned` с причиной `reconciled`. `accept` архивирует эту контрольную точку и сохраняет расход.
Точная повторная доставка не добавляет событие; явное замещение решения не отказывается
от того же повтора второй раз. Ручной `retry` разрешает одну попытку, но не создаёт событие
автоматического допуска `retry.admitted`. Прерывание само по себе сохраняет задержку;
массовой перезаписи старых журналов нет. Ошибка фиксации/допуска откатывает связанные
состояние и события.

Пауза запрещает новый допуск, но задержка по часам продолжает идти; после её истечения
продолжение может допустить попытку сразу. Смерть supervisor во время задержки сохраняет
срок; нужно продолжение **того же** запуска и проверка владения. После допуска то же
решение не разрешает ещё одну неопределённую попытку.

Задержка до MAX_SAFE_INTEGER сохраняется через короткие отменяемые ожидания. Если
абсолютный срок не представим безопасно, `dueAt`=`null`, а `scheduledAt`+`delayMs` остаются
основанием расчёта; это не немедленный повтор. `collect` ждёт окончания повторов ребёнка
и фиксирует финальное значение/ошибку один раз. Независимые `await` работают; запланированный
повтор не даёт всему запуску статус `waiting`. Отмена не превращается в собранную ошибку.

### Инспекция и учёт

`run.retries {id,key,after:0,limit:100}` (MCP `run_retries`, только чтение) листает
неизменяемые решения по `seq`; `current` отдельно показывает прогресс. Передавайте `nextAfter`
пока `hasMore`. Решение доказывает планирование, не допуск: нужны история попыток и события
`retry.admitted`. Каждый новый вызов имеет свои ID отчётов и учёт попытки; все токены
неудачных ответов остаются в суммах, отсутствие данных означает неполноту. Раунды
исправления формата относятся к той же попытке.

CLI/watch/браузер используют `retryingKeys`. Задержка не считается активным исполнителем
и не делает структурного родителя активным. «Сейчас», граф и детали узла показывают
политику, ожидающий повтор и страницы решений. Обновления только часов не дублируют логи
и не сбрасывают страницы. Версии v6/v7 и эталонные планы — [общая таблица](execution-plan.md#versions).

<a id="output-repair"></a>
## Исправление формата в той же сессии

После настоящей работы исполнитель с правом записи может прислать неправильный JSON.
Повтор задания ради формата опасен; `agent.config.outputRepair` управляет дополнительными
ходами внутри того же вызова:

```json
{"outputRepair":{"mode":"submit-only"}}
```

По умолчанию — `{mode:"disabled"}`. У `submit-only` нет неявных лимитов раундов/токенов/времени;
положительный безопасный целый `maxRounds` ограничивает дополнительные раунды только явно.
Раунд — один ход ассистента, включая только текст или вызовы запрещённых инструментов.
Исчерпание даёт типизированную ошибку `output`, не повтор всего задания.

Первый запрос использует исходные зафиксированные инструменты. Только после полного
завершения работы отсутствие результата, несоответствие схеме или несколько отправок
могут перейти к исправлению. Набор активных инструментов SDK заменяется одним `submit_result`:
остальные семь, включая `read`, недоступны; выдуманный `write`/`edit`/`bash` получает ошибку
инструмента. Схема не меняется; каждый раунд должен дать ровно один валидный результат.
Состояние отвергнутых отправок сбрасывается между раундами, история и эффекты сохраняются,
задание не отправляется снова. Инструкция запрещает выдумывать доказательства или менять
вердикт ради схемы.

Ранее допущенные вызовы инструментов завершаются до этой границы; исправление их не
откатывает и не гарантирует остановку запущенных ими внешних процессов. Расширения,
повторы SDK и автоматическое сжатие контекста остаются отключены. Ошибки `configuration`/
`resource`/`provider`/`protocol`/`cancel` не входят в исправление; отказ провайдера внутри
исправления завершает вызов. Смысловые проверки после исполнителя (например соответствие
`artifactRevision`) остаются ошибкой: формат не доказывает артефакт, тесты или приёмку.
Закрытие инструментов не превращает ранее пишущий вызов в вызов только для чтения.

Исправление — уже допущенная работа: пауза дожидается её и не ограничивает бесконечную
политику форматирования. Отмена прерывает сессию, очищает очереди и ждёт завершения
очистки. Авария не разрешает перезапуск пишущего исполнителя. Следующее разрешённое
посещение узла с `continue-node` может использовать историю и восстанавливает полный
зафиксированный набор инструментов нового вызова.

### Прогресс и расход исправления

`output.repair` содержит `round`, `status` `running`/`succeeded`/`invalid`/`failed`, исходную `cause`
`missing`/`schema`/`duplicate` и курсоры `afterReport`/`throughReport`. Supervisor атомарно пишет
`metadata.outputRepair` и событие activation.metadata с `key`/`attempt`. Текущие метаданные
показывают последний раунд, события — предыдущие. Замена попытки архивирует метаданные
и очищает их для новой. Раунд не является новой попыткой/посещением.

ID отчётов возрастают внутри вызова от первоначальной работы через все раунды.
Отчёты завершённого раунда лежат в `(afterReport,throughReport]` **того же `run`/`key`/`attempt`**
в `run.usage`. Они сохраняются до проверки результата и считаются один раз. Прогресс
`running` ещё не означает окончательную границу отчётов, текущий расход уже виден в учёте.
Прерванные/несообщённые ответы остаются неполными. Застывший `running` на остановленной
активации означает неподтверждённое завершение, а не продолжающуюся работу.
Детали узла/попытки показывают раунд/диапазон; watch — изменения без дубликатов от часов.
Здесь `succeeded` означает только валидный формат. Зафиксированная политика v4+ и
совместимость v1–v3 с `disabled` — [версии](execution-plan.md#versions).

Проверочные исполнители записывают реальный файл до ошибки вывода и подтверждают
отсутствие повтора всего задания. Проверка повторов SDK сохраняет расход шести вызовов,
включая неудачные ответы. Тесты журнала/интерфейса проверяют атомарность прогресса,
попытки и сохранение ожидающего повтора вне короткой недавней истории. Это проверки
установленной интеграции без моделей, не всех возможных API провайдеров, будущего SDK
или реальных квот.

Временные примеры для браузера без моделей: `spikes/ui-failure-smoke.ts`,
`spikes/ui-provider-smoke.ts`, `spikes/ui-output-repair-smoke.ts`,
`spikes/ui-retry-smoke.ts`, `spikes/ui-provider-retry-smoke.ts`.
Пример повтора создаёт запуск на паузе, затем делает отсутствовавшую команду доступной;
продолжение в панели показывает допуск/архив. SIGINT/SIGTERM завершает его работу
и удаляет только временный каталог. Запуск: `node --import tsx spikes/<name>.ts`.
