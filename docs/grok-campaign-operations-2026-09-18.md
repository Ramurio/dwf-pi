# Запуск кампании и восстановление после сбоев

Дата: 18 сентября 2026. Дополнение к [каталогу 180 заданий](grok-campaign-2026-09-18.md).

Статус: план. Воркфлоу, контейнеры и агенты при подготовке документа не запускались. Защита, описанная как будущая подготовка, пока не установлена.

## Главные решения

Кампанию выполняет dynamicwf. Её рабочая версия отделяется от исследуемых и изменяемых исходников. Исследования делятся на независимые тематические runs; параллельность внутри них задаётся штатными parallel/map. Исправления проходят отдельными пакетами и не обновляют движок, управляющий текущей кампанией.

Для первой волны из 24 тем удобно шесть тематических runs по четыре темы. Два исследователя каждой темы независимы; проверяющий получает оба результата после них. Это 48 исследовательских и 24 проверочных задания, плюс сводки. Число одновременно исполняемых задач определяется после контрольного запуска по фактической нагрузке; число заданий не означает одновременный запуск всех стадий.

## Что действительно есть в текущем коде

- run-controller.ts запускает supervisor.ts из установленной копии dynamicwf.
- process-client.ts запускает pi-worker-process.ts и check-worker-process.ts по путям относительно того же пакета; новые процессы читают файлы с диска.
- generated-module.ts проверяет sourceHash сгенерированного плана, но разрешает expressions.ts и Effect через текущую установку. Замороженный план не является снимком всего runtime и node_modules.
- Поэтому изменение используемого checkout или зависимостей может затронуть последующие workers и восстановление запуска. Уже загруженный код в живом процессе не делает все будущие процессы независимыми от диска.
- Worktrees разделяют рабочие файлы, но используют общую Git administration. Permission workspace-write и рабочий cwd не являются OS sandbox.
- При потере IPC с supervisor pi-worker-process.ts отменяет запрос. Независимость от вызывающего harness не означает независимость worker от его supervisor.
- Есть durable checkpoints, owner fencing, подготовленный идемпотентный start, collect, attempt history, recovery/reconcile и continuation. Эти механизмы не доказывают отсутствие внешних эффектов, которые произошли до потери checkpoint.
- Готового контейнерного executor в текущем process-client.ts нет. При обследовании docker/podman/colima/limactl не обнаружены в PATH; наличие sandbox-exec само по себе не доказывает проверенную изоляцию.

## Разделение файлов и ответственности

| Область | Назначение | Правило |
| --- | --- | --- |
| runner | Проверенная копия dynamicwf, её зависимости и зафиксированная версия Node | Не обновляется во время кампании; все управляющие команды используют явный путь к этой копии. |
| sources | Снимки текущего dynamicwf и remote-pi для исследований | Включают нужные незакоммиченные изменения и manifest; агентские исследования их не редактируют. |
| work | Независимые Git-копии для пакетов исправлений; worktrees внутри конкретного пакета | Результаты других исполнителей и исходный пользовательский checkout не являются общей рабочей папкой. |
| state | Отдельный журнал кампании и run resources | Не используется тестами изменяемого dynamicwf; тесты получают собственные временные store и HOME/profile. |
| artifacts | Отчёты, воспроизведения, проверенные commits/patches и индекс результатов | Сохраняются по завершению тем, а не только после общей агрегации. |
| backups | Согласованные копии состояния и экспорт принятых результатов | Находятся вне среды, в которой выполняются разрушительные эксперименты. |

Снимок рабочего дерева нельзя заменить одним git clone HEAD: оба исходных проекта содержат незакоммиченные изменения. Создать самостоятельную копию согласованного рабочего состояния, проверить её manifest и baseline. Не менять исходные ветки и не использовать общие writable node_modules или symlink из runner в редактируемый checkout.

Разные независимые Git-копии пакетов не выдаются штатному integrate как worktrees одного репозитория. Штатная интеграция выполняется внутри своего пакетного репозитория. Перенос принятого commit/patch между репозиториями — отдельная последовательная операция с проверкой конфликтов и итоговых тестов.

## Два этапа запуска

### Этап 1: исследования

Использовать явно настроенные read-only роли без bash/edit/write. Они читают снимки и возвращают отчёты через result tool; trusted экспорт сохраняет отчёты в artifacts. Это снижает риск случайной порчи файлов средствами агента, но не превращает процесс в OS sandbox.

Проверки, требующие исполнения кода, записи, сигналов процессам или искусственных отказов, оформляются отдельными заданиями второго этапа. Название роли verifier само по себе не является read-only настройкой: инструменты и permission задаются явно.

Рабочие исследования можно вести параллельно подготовке изолированного стенда. Не требуется сначала реализовать весь каталог функций безопасности.

### Этап 2: реализации и исполняемые проверки

Перед массовым предоставлением shell нужна проверенная граница ОС. Предпочтительная операционная схема для опасных пакетов — отдельный контейнер/VM с копией проекта, своим временным состоянием и ограниченно предоставленными ресурсами. Управляющий контур и резервные копии остаются снаружи. Рабочая копия runner предоставляется без возможности изменения.

Простой worktree, chmod файлов тому же владельцу и инструкция «не трогай соседние папки» такой границей не считаются. Агент с shell может сменить путь, попытаться изменить общий Git, послать сигнал другому процессу или запустить тест с неправильным store.

Подготовка изоляции — самостоятельный небольшой этап с отрицательными проверками:

1. Запись в runner, исходные проекты, основной state и соседний пакет должна быть запрещена ОС.
2. Процессы пакета не должны иметь возможности управлять процессами основного контура.
3. Проект, его тесты, Node и pi должны работать внутри разрешённых границ.
4. После остановки среды патчи и завершённые отчёты должны оставаться доступными снаружи.
5. Доступ к модели должен пройти реальный smoke test; размещение OAuth и обновление credentials продумываются явно. Не монтировать весь пользовательский home или управляющий socket контейнерной системы ради удобства.

Нативного per-worker контейнерного executor сейчас нет. Поэтому нельзя обещать, что помещение всего dynamicwf в один контейнер изолирует соседних workers друг от друга. Практический вариант без большой переделки runtime — изолировать отдельный пакет целиком вместе с его frozen runner и собственным store. Тогда падение его supervisor затрагивает этот пакет. Внутри пакета независимые writers всё равно получают worktrees; особо разрушительные испытания выполняются в отдельной среде.

Такие пакеты запускаются штатными authoring/start командами как отдельные runs; агентам не выдаётся право самостоятельно запускать скрытые workflows. Если минимальная изоляция не проходит проверку, продолжаются read-only исследования и подготовка исправлений как спецификаций; непроверенная среда не объявляется безопасной.

## Как не потерять остальные результаты

В независимых исследовательских ветках использовать явный collect. Ошибка одного исследователя сохраняется отдельно и не считается ни исследованием, ни голосом approve. Остальные ветви могут завершиться; сводка показывает полноту, ошибки и разногласия.

Не делать единственный финальный ответ единственным местом хранения всей кампании. Отчёт каждой темы и сводка каждой области сохраняются отдельно. Ошибка общего агрегатора не обесценивает уже завершённые отчёты; проверенные результаты можно использовать при явном продолжении.

Обычные исследовательские runs могут использовать один отдельный campaign store и общий UI. Испытания повреждения базы и изолированные пакеты имеют свои store. Один текущий dashboard не является готовым агрегатором разных stores: для изолированных пакетов первоначально достаточно индекса их ссылок и экспортированных результатов.

## Восстановление по видам отказа

| Сбой | Действие |
| --- | --- |
| Закрыли Codex, CLI или вкладку | Подключиться к тому же run через явный путь frozen CLI и тот же store. Это не повод создавать новый запуск. |
| Упал один исследователь | Сохранить ошибку и результаты соседей. Повтор разрешать по фактическому состоянию попытки и явно заданной политике для read-only/not-started. |
| Исполнитель успел изменить файлы и упал | Сохранить workspace, проверить diff, процессы и тесты; затем recovery/reconcile. Не считать отсутствие результата доказательством отсутствия записи. |
| Потерян ответ start/continue | Повторить тот же сохранённый запрос с тем же idempotencyKey. Не сочинять новый ID попытки. |
| Упал supervisor | Установить состояние workers и их групп; запросы могут прерваться из-за потери IPC. Затем восстановить управление тем же frozen runtime, используя checkpoint и явные решения об эффектах. |
| Сломан код в кандидатном checkout | Тесты кандидата падают; управляющий runner остаётся своей прежней версии. Пакет возвращается на исправление. |
| Обнаружен дефект самого frozen runner | Остановить допуск новой работы доступными средствами управления, сохранить состояние, воспроизвести дефект на копии и проверить исправление отдельно. Не заменять runtime работающих runs на лету. |
| Не работает обычное управление | Использовать внешний контроль ОС только для подтверждённых процессов этой кампании; общие pkill node/pi не применять. Сначала сохранить доступные факты и проверить эффект остановки. |
| База повреждена или недоступна | Прекратить записи и исключить оставшиеся процессы; сохранить повреждённую базу, восстановить проверенный backup отдельно, сверить более новые артефакты до возобновления. |
| Mac выключился | Запуски не работают без питания. После включения проверить процессы/журнал, затем recovery; не обещать продолжение каждого незавершённого модельного ответа. |
| Подписка закончилась или получен auth denial | Сохранить всё готовое и отметить незавершённые темы. Бесконечный retry авторизации и платный API fallback в кампанию не входят. |

Checkpoint восстанавливает уже записанные результаты. Ответ модели или файловый эффект, произошедший после последнего checkpoint, может требовать проверки или повторного исследования. Абсолютной гарантии exactly-once для произвольного shell нет.

Pause блокирует новые активации и ждёт активные; это не экстренная остановка работающего bash. Для прерывания есть cancel, после которого эффект записи всё равно может оставаться неизвестным. При потере управления запрещено запускать копию базы параллельно с ещё живыми исполнителями.

## Резервное копирование и наблюдение

Использовать согласованный SQLite online backup, а не копировать один state.sqlite во время записи с игнорированием WAL. Отдельно сохранять run resources, завершённые отчёты и Git-артефакты с manifest. Момент снимка и полнота незавершённых файлов должны быть явными.

До основной волны проверить открытие backup и восстановление тестового run на отдельном fixture. При рабочем восстановлении сохраняются ожидаемые пути либо отдельно проверяется перенос: plan/cwd/session paths могут быть абсолютными. Откат файла БД не откатывает файловые и внешние эффекты.

Наблюдение выполняется штатными UI/watch/status из frozen runtime. Нужна внешняя точка входа: файл с путём к runner, store, run IDs, сохранёнными start requests и командами контроля. Она читается обычным редактором даже при сломанном dashboard. Уведомление о пропавшем heartbeat не является разрешением перезапустить процесс.

## Порядок ближайших действий после команды запускать

1. Сохранить текущие рабочие состояния двух проектов и подготовить независимый runner с зависимостями; проверить исходный baseline.
2. Создать campaign store, каталог результатов и внешний файл управления. Привязать все команды к явному runner/store, не к изменяемому global CLI.
3. Выполнить маленький контрольный read-only workflow: параллельные ветви, намеренно неуспешная ветвь, collect, экспорт, pause/resume и идемпотентная повторная доставка start. Отдельно проверить backup/recovery на fixture.
4. Проверить доступ к native Grok и наблюдаемый xhigh. По фактическим latency, ошибкам и ресурсам выбрать размер первой одновременно исполняемой волны; не ставить токеновый бюджет ради экономии.
5. Запустить независимые исследовательские пакеты и сразу выдать реальные ID, watch и ссылки. Параллельно подготовить и испытать границу ОС для работ с записью.
6. Переносить подтверждённые задачи в изолированные пакеты реализации. Проверять конкретный артефакт независимым reviewer и тестами; интегрировать последовательно в кандидатную версию.
7. Завершить кампанию с проверенными результатами и сводкой неизвестного. Новую версию самого runner вводить отдельным переключением после проверки; текущая кампания не обязана переезжать на неё.

Для обычного восстановления внутри заранее согласованной политики не требуется каждый раз будить пользователя. Решения принимает управляющий агент по доказательствам и оставляет явную запись. Ситуации, где доказательств недостаточно, остаются unknown/inconclusive до проверки, а не превращаются в автоматический повтор.
