# Результат задачи и сохраняемое ожидание

Статус выполнения и решение о результате — разные данные. `succeeded` означает,
что граф завершился без технической ошибки. Поле `taskOutcome` содержит решение
`accepted`, `rejected`, `inconclusive` или совместимое со старыми запусками
`unclassified`, причину, массив evidence и источник `explicit` / `legacy`.

## Явное завершение

```json
{
  "id": "done", "kind": "finish", "decision": "accepted",
  "reason": {"op":"literal","value":"Проверки и независимые ревью приняты"},
  "evidence": {"op":"array","items":[{"op":"ref","path":["nodes","checks"]}]},
  "value": {"op":"ref","path":["nodes","artifact"]}
}
```

`finish` заканчивает текущий graph invocation и не имеет исходящих рёбер.
`reason` должен вычислиться в непустую строку, `evidence` — в JSON-массив.
`value` возвращается как обычный output. Решение root-графа становится итогом run;
решения вложенных графов остаются в их activation metadata и не подменяют root.
Evidence сейчас хранит объявленные ссылки/результаты. Runtime ещё не доказывает
их применимость к конкретному artifact digest: это отдельная работа по артефактам.

Старый `end` продолжает работать: `output.accepted:true/false` даёт legacy
accepted/rejected, любое другое значение — unclassified. Явный finish имеет
приоритет над похожими полями внутри output. Историческим данным не приписываются
новые доказательства. Preset сохраняется только после succeeded + accepted.

## Ожидание как часть графа

```json
{
  "id":"missingEvidence", "kind":"await",
  "reason":{"op":"literal","value":"Нужен результат проверки совместимости"},
  "input":{"op":"ref","path":["nodes","review"]},
  "responseSchema":{
    "type":"object",
    "properties":{"compatible":{"type":"boolean"},"reason":{"type":"string","minLength":1}},
    "required":["compatible","reason"],"additionalProperties":false
  }
}
```

Это иллюстрации узлов, а не целые запускаемые графы: ссылки должны существовать
в авторском workflow. `await` имеет обычные исходящие рёбра. Его output — ответ,
проверенный по зафиксированной JSON Schema без приведения типов/удаления полей.
Схема должна иметь корневой тип object; поддерживается тот же строгий набор
JSON Schema, что и для worker outputs. Неверная схема обнаруживается до запуска.

Причина, вход, схема и уникальный wait ID сохраняются в SQLite. ID привязан к
run + scope + node + visit; повтор восстановления не создаёт новый запрос, а
следующий проход цикла или другой элемент map создаёт свой. Когда все исполняемые
листья ждут, run имеет статус `waiting`; остальные параллельные ветки продолжаются.
Это не ручная пауза и не обязательный approval от человека.

```sh
dynamicwf run.waits <<'JSON'
{"id":"run-RETURNED-ID"}
JSON
dynamicwf run.resolve <<'JSON'
{"id":"run-RETURNED-ID","waitId":"wait-RETURNED-ID","response":{"compatible":false,"reason":"Не совпадает формат"},"resolvedBy":"agent"}
JSON
```

MCP: `run_waits` и `run_resolve` с теми же полями. `resolvedBy` — описательная
метка клиента, не аутентифицированная личность. В браузере раздел «Сейчас» показывает
причину, вход и схему, JSON-форму и ошибку проверки. При обновлении данных и переходе
между вкладками черновик сохраняется в памяти страницы. Reload его пока не сохраняет.

Ответ и событие `wait.resolved` фиксируются одной транзакцией. Повтор того же ответа
идемпотентен, конфликтующий ответ отклоняется; первая метка источника сохраняется.
Нельзя ответить на новый запрос уже завершённого/отменяемого run. Исторические
незакрытые запросы остаются видны API после отмены, но больше не принимают ответ.

## Пауза, смерть процесса и восстановление

Ручная пауза может завершиться при активном await: в нём нет исполняющегося worker.
Ответ разрешено сохранить на паузе; выполнение продолжится после `run.resume`.
Resume без ответа не разрешает ожидание. При подтверждённой смерти supervisor
сервис может запустить тот же run при `run.resolve`, сохранив ID ожидания и
завершённые checkpoints. Просто закрытый harness не требует восстановления.

Worktree в фазе `children` повторно подключается после проверки принадлежности
ветки/пути/репозитория, Git-состояния и base. Завершённые дочерние записи не
повторяются, незакоммиченные файлы сохраняются. Это разрешение не распространяется
на неопределённый результат дочернего agent/check или прерванный allocation/commit.
Для таких случаев по-прежнему требуется reconciliation; `run.resolve` его не заменяет.

Finish/await появились в compiler/runtime v2, запись переходов — в v3.
Новые планы используют v3. Проверка и запуск сохранённых v1/v2-планов
сохраняют исходные байты/hash; новые узлы в v1 запрещены. Старый runtime не получает
поддержку новых планов. SchemaVersion графа остаётся 1 с добавленными видами узлов.
Адресуемый prepare и общая политика upgrade/migrations ещё находятся в общем плане.

## Проверки

`tests/await-outcome.test.ts` исполняет detached-процессы без моделей: явные решения,
запрет сохранения непринятого preset, golden v1 plan, принудительный SIGKILL и новый
service, schema error/повтор ответа, pause→answer→resume, независимые map waits,
cancel, worktree reattach, root/child outcomes и browser API с conditional routing.
`tests/run-store.test.ts` проверяет fencing и откат ответа при ошибке записи события.

Ручной browser fixture:

```sh
node --import tsx spikes/ui-await-smoke.ts
```

Открыть напечатанную ссылку, проверить неверный тип, исправить ответ, поставить паузу,
сохранить ответ и продолжить. Ctrl+C отменяет незавершённый fixture, дожидается
остановки процессов и удаляет только его временные данные.
