## 1. Смысл отдельно от расположения

У diagram-design семантический паттерн отвечает на вопрос читателя, а визуальный
тип задаёт геометрию. Например, выяснить причину разных решений — semantic pattern
paired policy-evaluation traces; расположить его можно как flowchart.

Для dynamicwf это означает общий набор данных с несколькими проекциями:

| Вопрос пользователя | Представление | Необходимые факты |
| --- | --- | --- |
| Что вообще должно происходить? | Обзор схемы | Frozen definition, входы, условия, вложенные scopes |
| Где мы сейчас и почему ждём? | Активный путь и очередь | Activation, причина ожидания, реально объявленная concurrency |
| Что выполнялось одновременно? | Временная шкала по веткам/агентам | Начало/конец попыток, паузы, интервалы ожидания |
| Почему второй проход принят? | Сравнение проверок/решений двух проходов | Версия артефакта/критериев, test/review records, выбранные переходы |
| Куда ушли токены? | Полосы расхода и накопительный график | Поответный ledger, время, модель, полнота метрик |
| Что получилось? | Результат, файлы и diff | Outcome и применимые доказательства |

Не стоит требовать, чтобы один canvas одновременно отвечал на все эти вопросы.
При переходе между представлениями сохраняется выбранная activation/итерация.
Роль может повторяться в нескольких workers, поэтому временная дорожка должна
идентифицировать конкретную ветку/попытку, а группировка по роли быть опцией.

Источники reference: `references/semantic-patterns.md`, ADR 0002.

## 2. Связи должны читаться и различаться

Из dependency/flowchart примеров стоит перенять:

- Отдельные точки присоединения для нескольких рёбер одного узла.
- Внешние дорожки для обратных переходов, обводящие весь затронутый блок.
- Подписи на свободных участках маршрута, с подложкой и зазором от линии.
- Явное различие пересечения линий и их соединения.
- Одинаковую семантику направления и обозначений во всех вложенных графах.

В текущем `layoutGraph` все обычные исходящие рёбра начинаются в центре нижней
границы, а входящие заканчиваются в центре верхней. Изгибы строятся без поиска
препятствий. Дополнительная локальная проба с двумя рёбрами между одними узлами
получила два полностью одинаковых `path` и одинаковые координаты подписей.
Рёбра присутствуют в данных, но визуально не различаются.

Предлагаемая доработка: стабильные порты и ID рёбер, раскладка с учётом циклических
групп, маршрутизация мимо прямоугольников узлов и резервирование места для подписей.
Сначала проверить на наборах: ромб с join, два условия в одну цель, несколько
петель, self-loop, длинный обходной переход, широкий fan-out и русские подписи.
Выбор конкретной layout-библиотеки потребует отдельного сравнения на этих fixtures;
в diagram-design координаты примеров заданы вручную, автоматического решения нет.

Сохранять позиции уже существующих узлов при обновлении статуса. Для динамического
fan-out — контейнер с числом элементов и раскрываемыми экземплярами. Новая ветка
не должна без команды пользователя менять камеру или уводить выбранный узел.

## 3. Обзор без потери деталей

У reference есть небольшой бюджет элементов и идея скрывать богатую информацию
за устойчивым ID. Нам подходит принцип, но не фиксированные лимиты иллюстрации.

Обзор run может содержать 5–8 смысловых групп, например:
план → реализация → проверки → council → интеграция → результат.
Каждая группа показывает количество активных/готовых/проблемных экземпляров,
расход и наличие ожидания. Раскрытие сохраняет все реальные узлы и переходы.
Числа здесь ориентир читаемости обзора, а не ограничение размера workflow.

Узел на canvas: понятное действие, статус, длительность, токены, индикатор проблемы.
Inspector: полный путь, проход/попытка, вход/выход, артефакт, критерии, событие
перехода, исходные отчёты usage. Полный prompt и журналы — отдельное раскрытие.

Для deep link нужна составная идентичность: run + graph/scope + node + visit +
attempt. Одного `nodeId` недостаточно при map и loops. HTML-атрибуты могут отражать
эту идентичность для навигации и тестов, но не заменяют записи runtime.
В reference registry выводится из HTML; у нас правильное направление обратное:
journal/plan → общая проекция → браузер и экспорт.

Источники reference: ADR 0010, `references/export-registry.md`.

## 4. Сравнение проходов и объяснение решений

Особенно полезен paired policy-evaluation traces: одинаковые правила рядом,
явные статусы и первое расхождение. Для council пользователь должен видеть:

| Проверка | Проход 1, artifact A | Проход 2, artifact B |
| --- | --- | --- |
| Тесты | Не прошли: конкретный тест | Прошли |
| Correctness reviewer | Не запускался из-за тестов | Approve |
| Documentation reviewer | Не запускался из-за тестов | Inconclusive: отсутствует пример |
| Решение policy | Вернуть на исправление | Ждать недостающие данные |

Это иллюстративный сценарий, не данные пользовательского run.
`SKIPPED`, «ещё не дошли», отменено, упало и отрицательное решение должны различаться.
Если журнал не позволяет установить, почему узел не запускался, показывать
неизвестность. Не выводить причину из серого цвета или отсутствия activation.

Нужны события выбранных рёбер и проверенные policy results. В текущем compiler
`chooseEdge` выбирает следующий узел без отдельной записи о причине перехода.
Сравнение проходов также требует версии критериев: изменённое правило нельзя
показывать как прямое улучшение результата на том же правиле.

## 5. Визуальные проверки как контракт

Reference содержит не только советы о красоте. ADR 0005 объясняет реальный дефект:
маски подписей перекрывались позже нарисованными узлами, хотя остальные проверки
проходили. Геометрический checker и отрицательные fixtures сделали это проверяемым.

Для dynamicwf полезны три уровня:

1. Структура: все узлы/рёбра сохранены, уникальные ID, ссылки ведут к нужной попытке.
2. Геометрия: карточки/подписи не перекрываются, маршруты не проходят через посторонние
   узлы, несколько рёбер не рисуются одним путём, фокус и выбранный узел сохраняются.
3. Render: реальные длинные подписи, fallback fonts, масштаб, узкое окно,
   светлая/тёмная тема, клавиатура, reduced motion, загрузка истории во время обновления.

Их `verify-geometry.py` использует regex и эвристики размеров статических `<rect>`.
Наши узлы рисуются внутри SVG `transform`, поэтому прямое копирование checker
не подтвердит корректность координат. Использовать собственную layout-модель
для геометрических assertions и реальные browser bounds для проверки отрисовки.

Интересна методика `lint-render.py`: сравнить изображение с обычным clipping и
с последовательно освобождённым overflow, чтобы увидеть отрезанные штрихи/текст.
Но canvas нашего приложения намеренно обрезается viewport при pan/zoom; тест должен
проверять целевой режим fit/export и карточки, не объявлять любой выход за экран багом.
Сам checker документирует пределы и состояние unmeasurable — это тоже стоит перенять.

## 6. Спокойное оформление и движение по фактам

Полезны тонкие границы, ясная иерархия типографики, сдержанный фон, единая сетка
отступов и умеренные акценты. Цвет статуса дублируется текстом и значком.
На работающем мониторе может быть много ошибок одновременно: ограничение reference
«не более двух акцентов» не должно скрывать реальные проблемы.

Live-обновление показывает факты journal. Проигрывание истории — отдельный режим
с выбранным event cursor и кнопками шагов. Его пауза останавливает только просмотр;
операционная пауза workflow остаётся отдельной командой. Reduced motion отключает
декоративные перемещения, сохраняя обновление данных и доступность всех шагов.
Не копировать ограничение reference, которое скрывает playback-controls целиком:
в нашем интерфейсе переход по журналу полезен и без анимации.

Стабильный снимок для просмотра/экспорта должен указывать run, plan hash и event
cursor. Внешние шрифты из templates стоит заменить локальными или системными,
чтобы локальный монитор одинаково работал без сети. Экспорт — по явному действию,
из одной проекции, с выбором включаемых деталей.

## Дополнительные идеи и границы переноса

- Project marker и отдельные пользовательские профили переживают обновление
  установленного пакета. Для наших roles/prompts полезно фиксировать эффективный
  результат project/global выбора в плане, не менять общий установленный skill
  ради одного проекта. Источник: ADR 0006.
- Mermaid/draw.io можно позже импортировать в черновик, сохраняя соответствие
  исходным ID и список неподдержанных элементов. Геометрическая стрелка ещё не
  определяет исполнение, policy, инструменты или output schema. Такой импорт
  требует заполнения контрактов и обычных validate/prepare перед start.
- Bar chart и накопительная линия подходят для токенов лучше декоративного
  Sankey: переход workflow не переносит сохранённое количество токенов между
  узлами. Диаграмма потоков здесь легко создаст неверную интерпретацию.
- Не заимствовать лимиты 9 узлов/1 цикла/8 animation steps как ограничения runtime,
  ручную SVG-разметку каждого run, запрет JS для живого приложения и editorial
  шрифты/размеры без проверки читаемости рабочего монитора.
- В checkout основной код помечен MIT, отдельные assets имеют собственное
  происхождение в `THIRD_PARTY_LICENSES.md`. При фактическом переносе файлов
  нужно сохранить относящиеся к ним notices. В этом аудите код/assets не копировались.

## Как встроить в общий план

Сначала достоверные outcome/await, общая проекция и transition events.
Параллельно по смыслу этой работы можно улучшать маршруты и доступность текущего
canvas — эти улучшения не зависят от нового workflow primitive.
Затем обзор с раскрытием scopes, timeline и сравнение двух проходов.
После появления artifacts — связать их с review/diff и итогом запуска.
Экспорт и импорт схем полезны следующими шагами, когда основные представления
уже читаются и не расходятся с состоянием runtime.
