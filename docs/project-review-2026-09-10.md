## Что уже сделано удачно

- CLI и MCP используют один service. Выполнение живёт в отдельных процессах и
  сохраняется после закрытия вызывающего harness.
- Граф является данными; компилятор сам генерирует TS + Effect. Автору не нужен
  собственный scheduler. Условия, циклы, map и вложенные scopes уже реализованы.
- План сохраняет реальные model/thinking, prompts, schemas и байты выбранных skills.
  Изменение draft после старта не меняет активный run.
- SQLite journal атомарно записывает результаты/checkpoints, контролирует владельца
  supervisor и не разрешает молча повторять неопределённые внешние действия.
- Пауза с завершением текущих workers отделена от отмены. Process-group cleanup
  проверяется тестами с дочерними процессами, включая устойчивых к SIGTERM потомков.
- Worktree и явная интеграция дают полезную координацию Git. Проверяются принадлежность
  source текущему run, чистота workspaces и фактический commit перед merge.
- Reviewers по умолчанию получают свежие сессии и структурированные вердикты.
  Ограничения прав и воспроизводимости описаны без обещания OS sandbox.

Эти решения стоит сохранить. Текущие ограничения не требуют смены Effect, SQLite
или pi. При этом независимость от harness не равна автоматическому восстановлению
после любых ошибок, а воспроизводимость настроек не гарантирует одинаковый ответ LLM.

## Подтверждённые ограничения

| Случай | Фактическое поведение | Практическое последствие |
| --- | --- | --- |
| `end` возвращает `{accepted:false}` | Run получает `succeeded`; `preset.save` принимает его | «Успешно исполнен» используется как основание для «проверенного пресета» без проверки результата задачи |
| `check` делает `exit 1`, затем безусловное ребро в `end {accepted:true}` | `validate` возвращает `valid:true`; run завершается с `accepted:true` | Автор может забыть обработку результата проверки; структурная валидация этого не замечает |
| `prepare` revision 2, затем patch revision 3 и `run.start {id}` | Запускается revision 3 с другим plan hash | Предварительно просмотренный план не является передаваемым в start подтверждённым снимком |
| Команда check не существует, run стал `failed`, вызывается `run.resume` | Состояние остаётся `failed` | Кнопка resume не является восстановлением неуспешной задачи |
| Первый transform читает результат будущего узла | Граф валиден; вычисление падает с `No completed value at nodes.later` | Существование имени узла проверяется, доступность его результата на данном пути — нет |
| В журнале записан `running`, но PID не принадлежит supervisor | `watch --once` показывает «В РАБОТЕ»; `run.status` определяет `interrupted` | Два интерфейса могут по-разному описывать фактическую живость одного run |

Первые два случая не означают, что движок неверно исполнил указанные ему рёбра:
он исполнил их буквально. Проблема в недостатке контракта результата и проверки
намерения автора. Браузер уже отдельно выделяет `accepted:false`, но этот признак
остаётся соглашением о поле в произвольном JSON и не управляет lifecycle/presets.

## 1. Явный результат задачи и остановка внутри графа

Сейчас `end` возвращает любое JSON-значение. Отдельного узла ожидания/паузы нет;
pause доступна только внешнему управляющему клиенту. Поэтому skill предлагает
при `inconclusive` приостановить run из harness, который к этому моменту может быть
уже закрыт. Эта зависимость особенно заметна в продукте с самостоятельным supervisor.

В пользовательском JSONL demo `inconclusive` ведёт в `end {accepted:false}`,
а провал rootTests после интеграции — в `end` с причиной `integrated_tests_failed`.
В реальном run эти пути не понадобились: задача завершилась с `accepted:true`.
Но успешный проход не проверил их поведение.

Предлагаю отдельно хранить техническое состояние исполнения и результат задачи.
Для завершения нужны объявленный outcome, причина, ссылки на результат и доказательства.
Для ожидания — причина остановки и контракт того, что позволит продолжить.
Названия вроде `finish` и `await` здесь — предложение API, не существующие команды.

Ожидание должно быть частью зафиксированной схемы: worker возвращает данные о
препятствии, условное ребро приводит в `await`, runtime сохраняет это состояние.
Разрешить ожидание может другой агент или пользователь через тот же service.
Топология активного графа при этом не меняется. Пауза по кнопке остаётся отдельным
операционным действием и не требует обязательного запроса человеческого одобрения.

Приёмка: `inconclusive` переживает закрытие harness и supervisor/recovery;
в UI указаны причина и нужные данные; продолжение не повторяет завершённые узлы.
Отказ в приёмке не получает метку проверенного успешного пресета. Экспортировать
неудачный процесс для доработки можно отдельным действием, без такой метки.

Для устройства ожиданий полезен существующий паттерн message passing: Temporal
разделяет доставку Signal/Update и ожидание условия в workflow. Здесь можно
использовать этот принцип в собственном журнале, сохранив нынешний backend.
[Temporal: ожидание сообщений и условий](https://docs.temporal.io/develop/typescript/workflows/message-passing#add-wait-conditions-to-block).

## 2. Восстановление как законченный пользовательский сценарий

Защита от повторения внешнего эффекта правильная, но путь разрешения неопределённости
сейчас обрывается. `beginActivation` запрещает повтор любого неуспешного side-effect
узла. К ним относятся все agents, включая read-only, checks, worktree и integrate.
Публичного инструмента reconciliation/retry authorization нет. `failed` является
терминальным состоянием, и resume его не меняет.

При этом SDK retries отключены, неверный или отсутствующий `submit_result` завершает
worker ошибкой. Ошибка одного ребёнка обычного `parallel` распространяется на весь
Effect, поэтому инфраструктурная проблема одного reviewer может оборвать остальных.
Нужно различать ошибку доступа, временную ошибку транспорта, неправильный формат
ответа, отрицательный вердикт и неизвестный исход записи.

Предлагаемый порядок:

1. Ввести типизированные ошибки и признак определённости внешнего результата.
2. Добавить явную policy повторов для безопасных случаев, отдельно от repair-loop.
   Не повторять целиком пишущего worker только потому, что он неверно оформил ответ.
3. Дать возможность исправить формат финального ответа в той же сессии с закрытым
   доступом к новым побочным действиям. Валидация результата остаётся строгой.
4. Для неопределённого эффекта показывать конкретный workspace/session/операцию и
   давать документированное разрешение: принять проверенный результат, повторить
   после сверки или завершить запуск. Решение записывается в journal с владельцем
   и условиями применения; ручное редактирование SQLite не является интерфейсом.
5. Для fan-out предусмотреть policy сбора результатов вместе с ошибками, чтобы
   council мог обработать техническую неудачу одной ветки как отдельное событие.

У worktree есть фазы allocating/children/committing/complete. Их можно использовать
при reconciliation: после проверки принадлежности и состояния продолжить работу
в существующем выделенном workspace, сохранив дочерние checkpoints.

Приёмка: сбой read-only reviewer не заставляет заново реализовывать код; неизвестная
запись не повторяется автоматически; все попытки и потраченные токены сохраняются.
Настройки повторов, concurrency и ожидания остаются явными. Произвольные лимиты
итераций или обязательные согласования по умолчанию добавлять не нужно.

[run-runtime.ts](../src/run-runtime.ts), 61–76 и 152–169;
[pi-worker.ts](../src/pi-worker.ts), 104 и 117–159;
[compiler.ts](../src/compiler.ts), 84–98.

## 3. Полный и объяснимый учёт токенов

Нынешняя сумма успешных workers считается без повторного добавления родительских
результатов. Но usage возвращается после проверки финального ответа, а в runtime
сохраняется после проверки schema и review binding. При исключении, отмене или
невалидном ответе расход этой попытки не попадает в итоговый отчёт. В текущих
worker events поле usage также отсутствует. UI честно маркирует неполные данные,
но не может восстановить то, что не записано.

Нужно записывать числовой usage по завершении каждого ответа модели независимо от
успеха узла. Ключ учёта должен различать run, activation, attempt и ответ модели;
повторная доставка события не должна удваивать сумму. Итог узла, ветки, итерации и
run получается из одних записей. Для оборванного ответа без отчёта провайдера надо
оставлять «неизвестно/частично», а не подставлять ноль или обещать точность.

Хранить стоит вход без кэша, cache read/write, выход, provider total, reasoning при
наличии, provider/model, источник учёта и оценку SDK. Reasoning в установленном pi
уже входит в output: повторно прибавлять его нельзя. Оценка SDK и реальное списание
по подписке — разные величины. Метрики должны показывать происхождение данных.

Сверка реального demo `run-0777991f-a942-430a-9b9c-382887927863`:

| Величина | Токены |
| --- | ---: |
| Вход без кэша | 118 829 |
| Чтение кэша | 176 128 |
| Запись кэша | 0 |
| Выход | 47 177 |
| Всего по SDK | **342 134** |

Эти числа получены из 29 assistant messages в пяти pi-сессиях и совпали с
сохранёнными worker totals. Кэш составляет 51,5% общего числа. Сейчас интерфейс
показывает вход и выход без отдельного кэша, поэтому их сумма визуально не объясняет
total. Для данного run это потеря детализации, а не ошибочная общая сумма.

| Работа | Токены | Время worker |
| --- | ---: | ---: |
| Planner | 28 757 | 3м 44с |
| Implementer | 122 153 | 4м 41с |
| Correctness review | 74 144 | 3м 7с |

они обнаруживают и устраняются ли эти дефекты на следующей итерации.

Приёмка: новый завершённый ответ увеличивает счётчик ещё до завершения worker;
отмена сохраняет уже известный расход; каждая сумма раскрывается до исходных
числовых записей; recovery и session continuation не удваивают расход.

## 4. Артефакт и доказательства приёмки как отдельные сущности

Сегодня runtime проверяет, что reviewer вернул ту же строку artifactRevision,
которую получил. Проверять соответствие этой строки реальным данным должен автор
графа. В demo снимок получают через `git write-tree`; exitCode этого check отдельно
не проверяется перед council. Коммит worktree происходит уже после дочернего графа.
Механизм интеграции проверяет фактический source head, но не связывает его с
конкретным review verdict или результатом теста.

Предлагаю неизменяемую запись Artifact: kind, digest/commit/tree, местоположение,
создавшая activation и при необходимости версия критериев. CheckResult и
ReviewResult ссылаются на неё. Базовые операции snapshot и проверка соответствия
артефакта должны принадлежать runtime: автору не нужно изобретать shell-команду
с идентификатором для каждого нового council.

Это даёт одновременно корректность и хороший UI: можно открыть проверенную версию,
diff между попытками, тестовый отчёт и замечания именно к этой версии.

Для нескольких coding-ветвей полезен отдельный integration worktree: объединить
кандидатов, проверить итоговую комбинацию, затем обновить целевую ветку при условии,
что её ожидаемый head не изменился. Сейчас при конфликте позднего source ранее
успешные merges сохраняются; это документировано и проверено тестом. Работа в
отдельном integration workspace уменьшит объём ручной сверки такого результата.
Это координация с проверкой Git-состояния, а не обещание полной транзакционности
произвольных пользовательских изменений файлов.

Приёмка: изменение файла после review делает старое approve неприменимым; тест
старого snapshot не подтверждает новый; конфликт или провал объединённых тестов
оставляет целевую ветку на исходном head. Никаких автоматических hard reset.

Источники: [run-runtime.ts](../src/run-runtime.ts), 152–178 и 186–199;
[workspaces.ts](../src/workspaces.ts), 38–50 и 53–98.

## 5. Составление графов должно требовать меньше ручной логики

Полный `examples/council.patch.json` занимает 1 078 строк. Размер JSON сам по себе
не дефект, но отражает объём повторяющихся bindings, структур результата и policy.
Агент должен одновременно помнить scope, первый проход цикла, reviewer contract,
порядок условий, snapshot и обработку каждого отрицательного результата.

Нужны два уровня одного authoring-интерфейса:

- Нынешние узлы и рёбра для произвольной композиции.
- Параметризованные рецепты для частых конструкций: produce→check→repair,
  independent council, map→collect→synthesize, worktree→review→integrate.

Рецепт должен раскрываться в обычный граф, который можно inspect/patch/validate.
Policy all/any/quorum/arbitration задаётся данными, dissent сохраняется. Рецепт не
должен превращаться во второй скрытый runtime или неуправляемого «суперагента».
Для динамического числа результатов понадобятся безопасные операции фильтрации,
подсчёта и агрегации коллекций, а не перечисление комбинаций голосов вручную.

В `validate` следует добавить понятные ошибки/предупреждения о потоке данных:
чтение ещё не полученного output, отсутствующее поле по известной schema,
необработанный enum-вердикт, check без объявленной политики exitCode,
константное условие, затенённый переход, approve без требуемых доказательств.
Нельзя обещать математически доказать произвольную LLM-задачу статическим анализом;
неоднозначные случаи должны становиться предупреждениями, а не ложными гарантиями.

Ещё два небольших, но существенных дополнения:

- Input/output schemas для workflow и подграфов: они дают раннюю диагностику и
  формы запуска preset в браузере.
- `workflow.simulate` с заранее заданными результатами узлов: перед inference
  прогнать approve, request_changes, inconclusive, failed checks и crash boundary.
  Это проверка процесса; качество ответов модели она не доказывает.

`prepare` стоит возвращать адресуемый plan ID/hash, а start должен уметь запускать
именно этот снимок. Также нужен idempotency key запроса start: если клиент не
получил ответ и повторил запрос, он должен получить тот же run ID. Сейчас каждый
start создаёт новый UUID, независимо от того, является ли запрос повторной доставкой.

Приёмка: новый агент без контекста реализации собирает и отрицательно проверяет
council через публичные tools; после start немедленно отдаёт run ID и ссылки.
Изменение draft после prepare не подменяет выбранный для запуска план.

[graph.ts](../src/graph.ts), 6–28 и 191–202;
[service.ts](../src/service.ts), 102–110;
[run-controller.ts](../src/run-controller.ts), 44–51;

указывает, что проверяющий имел более ранний контекст реализации; нужен и свежий.

## 6. Браузер как основной рабочий интерфейс

Текущий браузер уже позволяет наблюдать запуск и управлять им. Следующий результат
для пользователя — открыть run и понять цель, состояние, причину решений, готовые
файлы и возможное действие, не разбирая внутренние node IDs.

| Экран | Что добавить | Откуда должны приходить данные |
| --- | --- | --- |
| Обзор run | Задача, итог/препятствие, ссылки на файлы, проверки, действие для продолжения | Явный outcome, artifacts, ожидания |
| Граф | Человеческие названия, раскрытие вложенных групп, фактически выбранные стрелки и причины | Definition + события переходов с activation/visit |
| Временная шкала | Параллельность, паузы, попытки, просмотр состояния на выбранном checkpoint | Версионированные события и их проекция |
| Council | Матрица reviewer × критерий, вердикты, блокирующие findings и их устранение | Структурированные review/check records |
| Артефакты | Файлы/отчёты, commit и diff между итерациями, применимость review | Реестр неизменяемых artifacts |
| Токены | Расход по модели/агенту/ветке/итерации, кэш, незавершённый учёт | Общий usage ledger |
| Пресеты | Просмотр, явное сохранение, сравнение версий, копия в draft, запуск с параметрами | Тот же application service и input schema |
| Система | Настоящие model/tool capabilities, проблемы авторизации, версии и readiness | Doctor и доступный каталог |

События переходов нужны уже сейчас: compiler выбирает следующее ребро через
`chooseEdge`, но не записывает выбранное ребро и причину как отдельное событие.
Нынешние стрелки честно показывают возможные переходы. Их нельзя раскрасить как
исполненную трассу только по агрегированному зелёному статусу узлов.

Перемотка должна показывать состояние из журнала. Сама по себе она не должна
перезапускать действия. «Повторить с изменениями» создаёт отдельный run с явной
связью с предыдущим и проверенными правилами переиспользования результатов.

Приоритет UI: обзор результата, применимые действия, артефакты и объяснение
переходов. Затем библиотека и формы запуска. Графический редактор черновиков
полезен позже; редактирование топологии уже запущенного графа пользователю не нужно.

Сейчас client JS сам пересчитывает часть usage/status и распознаёт замечания регулярным
выражением по строке результата. Сервер работает напрямую с controller/store,
а watch читает store без сверки живости. Лучше вынести общую типизированную проекцию
состояния, liveness и outcome в application layer для CLI/MCP/browser/watch.
Она должна отдельно показывать факт последнего подтверждения живости и неизвестность.
Просмотр не обязан автоматически возобновлять или повторять работу.

Приятные небольшие улучшения: ссылки на run/узел/итерацию, сохранение выбора после
reload, кнопка перехода из terminal в browser, копирование команды подключения,
поиск по проекту, уведомление браузера о завершении/ожидании по настройке. На графе
достаточно компактных фактов; prompts и подробные tool outputs открываются отдельно.

## 7. Данные наблюдения нужно отделить от больших планов и результатов

В `RunStore.get` каждый раз выбирается и разбирается весь plan. Это происходит и
на heartbeat/control paths. `listRuns` сначала выбирает IDs, затем делает отдельный
`get` на каждый run; `listActivations` аналогично делает запрос на каждую activation.
`events(after)` имеет курсор, но не ограничение размера страницы. Браузер примерно
раз в секунду получает полный snapshot, а список запусков периодически пересчитывает
usage всех activations всех runs. Watch опрашивает журнал раз в 250 мс.

На текущем demo это не помешало работе. Для длительных loops, больших skill bundles
и многих runs это конкретные места роста нагрузки, а не доказанный нагрузочным
тестом предел ёмкости. Нагрузочный предел в этом аудите не измерялся.

Предлагаю отдельно хранить неизменяемые планы/skill blobs по hash, компактную запись
состояния run, попытки и usage; читать activations одним запросом, события — страницами.
Граф и настройки получать один раз, изменения состояния доставлять по event cursor
или SSE с возможностью восстановить пропущенные события. Потребуются версии событий
и миграции; полноценная внешняя event-stream платформа для этого не нужна.

Большие stdout/stderr checks и artifacts лучше сохранять потоково в локальные файлы,
а в journal держать ссылку, digest и краткое превью. Сейчас wrapper и parent собирают
строки целиком. Результат повторяется в checkpoint и event, а при передаче целиком —
ещё и в outputs родителей.
Это также улучшит просмотр длинных тестовых отчётов.

Очистка должна быть отдельным явным действием: показать размер runs/sessions/worktrees,
проверить принадлежность, наличие несохранённой работы и ссылки на artifacts/presets,
затем удалить выбранное. По умолчанию пользовательские результаты сохраняются.

Источники: [run-store.ts](../src/run-store.ts), 108–121, 253–255 и 289–292;
[supervisor.ts](../src/supervisor.ts), 27–36;
[check-worker-process.ts](../src/check-worker-process.ts), 26–39;

## 8. Настройки контекста и расширение возможностей workers

Исследовательская роль сейчас по умолчанию имеет только read/grep/find/ls. Само
название `researcher` не даёт web search. В общем каталоге tools доступны семь
файловых/shell-инструментов; MCP интерфейс продукта обслуживает authoring/control,
но не подключает произвольные MCP tools внутрь pi worker.

Для заявленного использования в исследованиях полезнее добавить явно выбранные
search/fetch или MCP tool adapters с понятными схемами и правами, чем новые названия
ролей. Каталог должен показывать фактические возможности выбранного worker.
Версии схем/конфигурации tools фиксируются в плане, credentials остаются вне него.

Контекст тоже требует политики. Project AGENTS/SYSTEM/context files сейчас не
подключаются автоматически; worker может прочитать их инструментом, но обязательного
подключения нет. Для coding нужен явный выбор project instructions с записью
происхождения и snapshot, сохраняя отказ от случайной загрузки глобальных extensions.
Для пользовательских roles/prompts полезны project/global версии и просмотр
эффективной конфигурации до старта.

`continue-node` сохраняет полную историю, а auto compaction отключена. В длинном
repair-loop отсутствие лимита итераций не снимает ограничение контекстного окна
модели. Нужна настраиваемая политика: продолжать сессию, зафиксировать summary
и начать свежую либо передать следующему worker выбранные artifacts/findings.
Переход и содержимое переданного контекста должны быть видимы и учтены в usage.

Источники: [catalog.ts](../src/catalog.ts), 5–17 и 42–58;
[pi-worker.ts](../src/pi-worker.ts), 104–110;
[run-runtime.ts](../src/run-runtime.ts), 95–104.

## 9. Установка, совместимость и поддержка кода

Сейчас версия пакета `0.0.0`, установка создаёт symlinks в checkout, а CLI,
supervisor и workers загружают TS через tsx. Это удобно для разработки, но означает,
что обновление checkout/dependencies меняет runtime, на который рассчитывают
сохранённые планы. Версии compiler/runtime есть, но совместимость требует
регламента их изменения и тестов старых preset/run fixtures.

Нужны собираемый runtime, versioned install, команды version/doctor и понятное
обновление с возможностью сохранить предыдущую совместимую версию. Проверить
заявленную поддержку Node и POSIX в CI. Сборка JS entry points должна включать
актуализацию ссылок на `.ts` в child launchers и generated module loader.
Машинная генерация TypeScript + Effect при этом сохраняется.

Предупреждение DEP0205 — реальный долг загрузчика: `bin/dynamicwf.mjs` вызывает
tsx register; Node объявляет `module.register()` deprecated и направляет на
`module.registerHooks()`. Плановая сборка JS entry points снимает необходимость
этого loader на production-пути. Другой вариант — отдельно проверить совместимое
обновление loader. Глобальное подавление предупреждений не устраняет зависимость.
[Node.js: DEP0205](https://nodejs.org/api/deprecations.html#dep0205-moduleregister).

Grok bridge читает helper modules из отдельно установленного pi-xai-oauth 1.5.2;
проверяется package identity/version, но этот код не входит в lockfile проекта.
Нужен явный поддерживаемый контракт adapter/package fingerprint и отдельная
совместимость в doctor. Существующий узкий bridge полезнее сохранить до появления
проверенной замены. Название Heavy нельзя превращать в выдуманный model ID.

По поддержке кода: браузерный `app.js` уже около 980 строк и не входит в TypeScript
typecheck. Есть дублирование JSON validation, вычисления статусов и usage между
интерфейсами. Разделение API contracts, state projection и renderers даст больше
пользы, чем массовое форматирование или смена UI framework без конкретной нужды.

Источники: [package.json](../package.json), [bin/dynamicwf.mjs](../bin/dynamicwf.mjs),
[execution-plan.ts](../src/execution-plan.ts), 68–85;
[xai-provider.ts](../src/xai-provider.ts), 48–67;
[tsconfig.json](../tsconfig.json).

## Предлагаемая последовательность работы

| Этап | Законченный результат для пользователя | Зависимости и приёмка |
| --- | --- | --- |
| 1. Достоверное состояние | Понятно, выполнена ли задача, почему процесс ждёт, сколько известно о расходе | Outcome/await, общий liveness, usage по ответам; отрицательные сценарии и cancelled accounting |
| 2. Проверяемый результат | Открываются файлы, diff, тесты и review именно той версии, которую принимаем | Artifact records, правила applicability, integration workspace, обзор результата и council в UI |
| 3. Удобный повторяемый процесс | Агент быстро собирает workflow; пользователь запускает preset через форму | Рецепты, schemas, lint/simulate, start по plan hash и idempotency; свежий skill forward test |
| 4. Длительная повседневная работа | Ошибку можно разрешить, большой journal остаётся удобным, обновление предсказуемо | Reconciliation UI/API, context policy, paging/projections, retention, собранный versioned runtime |

Минимальный путь восстановления и сохранение всех попыток нужно проектировать уже
на первом этапе; четвёртый доводит его до удобного полноценного интерфейса.
Изменения query paths и packaging можно делать небольшими отдельными работами по
мере необходимости, не задерживая пользовательские улучшения до полного рефакторинга.

Регрессионный набор для следующих изменений должен включать: approve; repair после
request_changes; inconclusive с ожиданием; failed tests; устаревший artifact;
ошибку одного reviewer; отмену после расхода токенов; смерть supervisor в worktree;
повтор доставки start; изменение draft после prepare; конфликт интеграции.
Для каждого проверять runtime, API и видимый итог, а не только цвет узла.

После этого стоит оценивать качество council на задачах с заранее известными
дефектами: обнаружение, ложные замечания, повторяемость и устранение findings.
Количество reviewers и потраченные токены сами по себе не доказывают качество.

До появления конкретной потребности можно отложить удалённые executors,
многопользовательский SaaS, отдельный брокер очередей, marketplace и редактирование
активной топологии. Локальный service + SQLite + отдельные pi-процессы позволяют
реализовать перечисленные сценарии постепенно и сохранить независимость от harness.
