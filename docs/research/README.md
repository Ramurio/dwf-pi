## Главные выводы для выбора устройства

Официальные Claude Code Dynamic workflows очень близки к исходному пользовательскому
сценарию: описать процесс, наблюдать стадии, повторно использовать удачный запуск.
Там агент пишет JavaScript. Наше центральное требование сильнее в области authoring:
модель работает с блоками и рёбрами, а машинный компилятор отвечает за код.
[Официальный механизм](https://code.claude.com/docs/en/workflows)

Нужно заимствовать идеи по отдельным слоям, а не подключать все исследованные
фреймворки: графовые контракты LangGraph; авторинг n8n; границы устойчивого исполнения
Temporal/Hatchet/Inngest; структурную композицию Mastra; отделение обмена контекстом
от execution graph AutoGen; роль/flow separation CrewAI. Effect соответствует
заданному пользователем стеку, но выбор конкретного persistent backend ещё открыт.
Основания этих выводов и ссылки на каждый продукт приведены в матрицах ландшафта.

Рекомендуемая архитектурная граница: workflow engine владеет графом и журналом,
pi workers выполняют агентные активации. Роль, узел, активация и сессия — разные
сущности. Общая pi-сессия на весь workflow не даёт нужной независимости контекста.
Это проектный вывод, не технический запрет pi.

Три свойства нельзя обещать по наличию библиотеки: восстановление после crash,
изоляция действий агента и exactly-once внешних эффектов. Для них нужны отдельные
реализованные протоколы и интеграционные проверки; документы не называют их готовыми.
