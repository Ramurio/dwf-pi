# Учёт расхода

Начиная с обновления 2026-09-10 новые workers отправляют `usage.report` после
`message_end` каждого ответа модели. Это происходит до проверки `submit_result`,
review binding и итогового checkpoint. Записи сохраняются в отдельном SQLite ledger.

Идентичность записи: run + activation + attempt + reportId. Повторная доставка
идентичного отчёта идемпотентна; конфликтующее содержимое того же ID отвергается.
Запись, агрегат и событие `usage.reported` фиксируются одной транзакцией. Проверка
владельца supervisor применяется и к учёту. Следующая попытка имеет отдельное
пространство report IDs; следующая visit также получает отдельную activation.

Сохраняются input, output, provider total, cacheRead/cacheWrite, reasoning при наличии
и SDK cost. Reasoning является частью output. Не следует выводить total сложением
частичных полей разных провайдеров. Неизвестная детализация остаётся неизвестной.
Сессия индексируется при создании, поэтому её можно найти и после невалидного ответа.

Если breakdown есть только у части ответов, сохраняется известная сумма и
`partialFields` с именами неполных полей. В summary доступны независимые признаки
`cacheReadPartial`, `cacheWritePartial`, `reasoningPartial`, `costPartial` и число
activations, сообщивших соответствующие поля. Полный total не означает полный
breakdown. Полностью отсутствующее поле не становится известным нулём.

`usage.settled` сообщает полноту учёта независимо от успеха задачи. Например,
завершённый ответ с неверным результатом может иметь полный учёт; отменённый поток
оставляет неполный учёт, сохраняя все уже полученные числа. Жёсткое завершение
процесса не может восстановить расход, который провайдер ещё не сообщил.

```sh
dynamicwf run.usage <<'JSON'
{"id":"run-ID","after":0,"limit":100}
JSON
```

Ответ содержит `summary`, `reports`, `nextAfter`, `hasMore`. Для следующей страницы
передай `nextAfter` как `after`. Допустимый размер страницы 1–1000; это ограничение
размера ответа API, а не бюджета workflow. CLI и MCP используют один контракт.
Browser имеет такую же страницу числовых отчётов, доступную с вкладки «Токены».
Раскрытые страницы сохраняются при обновлении snapshot и переключении вкладок
или запуска. Ошибка загрузки сохраняет курсор; повтор продолжает с него.

Старые журналы открываются с добавлением новых таблиц. Их старые metadata.usage
сохраняются; поответные записи и cache breakdown для них не синтезируются.
Родительские structural outputs не учитываются второй раз.

`task.usage {id}` суммирует отдельные linked runs задачи. Нельзя складывать строки
отчётов, archived attempts и cumulative metadata одновременно. Повторно использованные
выходы не добавляют вызов модели и не считаются missing agent reports. Оценка SDK
не является счетом подписки; неизвестная стоимость не становится нулём. В браузере
можно переключить «Этот запуск» / «Вся задача»; исходный сбой остаётся видимым рядом
с активным продолжением. Переключение на unrelated task не сохраняет предыдущие
task totals; выбор связанного запуска той же задачи сохраняет режим всей задачи.

Проверено: настоящая pi SDK session с offline transport, отчёт во время следующего
хода, ошибка output schema, cancellation; journal durability, duplicate/conflicting
delivery, stale owner, rollback при ошибке event insert; CLI service/MCP schema и
browser HTTP pagination. Эти проверки не расходуют подписку.
