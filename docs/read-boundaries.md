# Подготовка материалов для read-only воркеров

## Проверенная граница

Регрессия `tests/read-boundary.test.ts` использует настоящий project-local
`@earendil-works/pi-coding-agent` 0.85.1 read, без модели и сети.
Текстовый ответ ограничен 2000 строками или 50 KiB (51200 байт).
Если первая выбранная строка сама превышает байтовую границу, SDK возвращает
предупреждение `firstLineExceedsLimit`, пустое `truncation.content` и ноль
`outputBytes`: содержимое строки **недоступно**, а не молча обрезано.
`offset` и `limit` считают строки, не байты. У однострочного JSON `offset=2`
уже за концом файла; уменьшение `limit` не открывает часть первой строки.

SDK предлагает `Use bash`, но это текст диагностики, не разрешение.
Offline worker fixture проверяет allowlist `read, submit_result` до и после
предупреждения и отказ при попытке вызвать отсутствующий bash. `write` и
`edit` также не появляются. Не выдавайте их read-only исследователю ради обхода.

## Что должен подготовить владелец входных данных

1. Сохраните оригинал и raw findings без потерь, отдельно от резюме и выводов.
   Не заменяйте исходные наблюдения пересказом и не обрезайте значения.
2. Для JSON с короткими значениями подготовьте многострочную копию (например,
   отступ 2), сохранив исходные типы и значения. Проверьте обратный разбор и
   равенство значений; храните raw оригинал отдельно (особенно если парсер
   может терять точность чисел или повторяющиеся ключи).
3. Читайте копию страницами по строкам, следуя offset в уведомлениях SDK.
   Тест восстанавливает JSON больше 50 KiB из страниц по 100 строк,
   проверяет начало, конец, точное совпадение текста и всех значений.
4. Pretty-print **не спасает одно огромное строковое значение**: сама строка
   остаётся больше 50 KiB. В тесте скобки читаются, значение — нет.
5. Для таких значений владелец заранее готовит отдельные UTF-8 текстовые части
   безопасного размера (например, до 16 KiB каждая, без разрыва UTF-8 символа).
   Не добавляйте в части разделители или новые строки, меняющие исходный текст.
   Приложите доступный многострочный manifest: источник и JSON-путь значения,
   кодировка, способ извлечения (raw байты или декодированное значение), порядок
   частей, имена, длины в байтах, SHA-256 каждой части и объединённого текста.
   Соединение байтов частей в указанном порядке должно воспроизвести выбранный
   текст с совпадающей общей контрольной суммой. Оригинал JSON и raw findings
   остаются отдельно. Это подготовка владельца, не новая возможность воркера.
6. Если подготовленных частей нет, явно укажите: «Содержимое недоступно через
   read: файл …, строка …, firstLineExceedsLimit; выводы по нему не сделаны».
   Не считайте полученное предупреждение прочитанным материалом.

## Точный scope / no-change

- `src/pi-worker.ts`: **no-change**; allowlist и запрет mutation tools для
  read-only остаются прежними, что дополнительно покрыто существующими тестами.
- Compaction: **no-change**, по-прежнему отключена (`enabled: false`).
- SDK read: **no-change**; граница документирована и воспроизведена, не исправлена.
- Общий byte-range reader — **будущий интерфейс**, здесь не реализован.
- Campaign packets, frozen runner и глобальная установка pi не изменялись.

Это доказательство недоступности длинной строки и проверка подготовки коротких
строк, не модельный эксперимент качества внимания. Lost-in-the-middle и влияние
полного большого input на качество остаются **недоказанными**.
