# Требования и доказательства завершения

Дата основания: 2026-09-08. Источник: исходная задача пользователя.
Статус: работа начата с пустой директории; Git инициализирован.

## Обязательная продуктовая цель

Агент из любого harness с доступом к установленному интерфейсу получает skill,
собирает workflow из блоков и связей, настраивает роли и запускает его на pi.
Агенту не требуется писать код оркестрации, циклы или функции маршрутизации.
Система машинно генерирует TypeScript + Effect по проверенной схеме.

| Требование | Доказательство для приёмки | Текущее состояние |
| --- | --- | --- |
| Широкое и глубокое исследование существующих workflow | Сравнение по архитектурным свойствам, первичные источники, выводы и ограничения | В работе |
| Особое внимание Claude Code dynamic workflows | Проверка именно официальной функции, authoring, execution, replay, presets, ограничения | В работе |
| Много вопросов до реализации | Отправленная анкета и сохранённые ответы либо явно указанные предположения | Вопросы отправлены |
| Графовый authoring инструментами | Создание, изменение, соединение, валидация графа без пользовательского JS | Не реализовано |
| Машинная генерация TS + Effect | Детерминированный компилятор; сгенерированный результат выполняется и соответствует схеме | Не реализовано |
| Последовательности, ветвления, циклы, возврат по ревью | Реальный workflow проходит review→fix→review до approve, включая отрицательные случаи | Не реализовано |
| Параллельные исследования/ревью | Несколько pi workers, правильное объединение результатов и ограничения параллелизма | Не реализовано |
| Продуманные примитивы | Каталог ролей и управляющих блоков, входы/выходы, defaults, проверка совместимости | Не реализовано |
| Настройки блока | Model, thinking, system prompt, tools, skills, permissions, session policy валидируются и реально применяются | Не реализовано |
| Pi как backend | Сквозной запуск с настоящим установленным pi, без зависимости от API родительского harness | Не реализовано |
| Переносимый skill и однократная настройка | Установка, prerequisites skill + CLI/MCP, отсутствие host-specific backend; отдельные сквозные проверки хотя бы двух клиентов | Не реализовано |
| Видимость текущего графа и стадии | Терминальное отображение реального состояния запуска, а не статическая картинка | Не реализовано |
| Библиотека пресетов | Сохранить удачный запуск, получить зафиксированные настройки, повторить с новыми входами | Не реализовано |
| Промпты, навыки, права | Полные поставляемые определения, реальные проверки доступов и тесты важных ограничений | Не реализовано |
| Вести Git | Осмысленные локальные коммиты; результаты проверок и открытая работа отражены в документации | Начато |

Визуализация и пресеты сформулированы пользователем как желаемые возможности;
в план включены, а не исключены ради более узкого MVP.

## Открытые уточнения, влияющие на устройство

Слово «динамический» может означать создание схемы под задачу, динамический fan-out
либо изменение топологии во время исполнения. Пользователю задан прямой вопрос;
нельзя молча подменять это статическим DAG без циклов.

Единица pi-сессии, модель памяти, durable recovery, Git-изоляция, budget policy,
remote execution и human gates требуют ответа либо явно обозначенного выбора.
Они не объявляются выполненными наличием типов или README.
«Любой harness» означает независимый backend и опубликованный контракт для клиента,
умеющего прочитать инструкции и вызвать CLI/MCP. Два успешных клиента подтверждают
две интеграции, а не совместимость со всеми существующими или будущими продуктами.

## Порядок проверки результата

1. Контрактные проверки authoring и компилятора: ошибки схемы, стабильность генерации,
   соответствие рёбер, портов и замороженных настроек.
2. Детерминированные сценарии runtime: fan-out/join, циклы, ошибки, cancel,
   лимиты, проверка выходов, конкурентные изменения и восстановление.
3. Интеграция с настоящим pi: применённые model/tools/skills/system prompt,
   вывод по схеме и прерывание процесса. Mock-only тесты это не доказывают.
4. Полный пользовательский путь: подключить skill, инструментами собрать схему,
   запустить, увидеть стадии, исправить по ревью, сохранить и повторить preset.
5. Проверить все строки таблицы по актуальному дереву, выводам команд и runtime.
   Не маркировать весь проект завершённым по одному зелёному тестовому набору.
